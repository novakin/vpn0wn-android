Review interface addresses, DNS, peer endpoints and AllowedIPs before connecting. Supported WireGuard config behavior belongs to [backend contracts](backend-contracts.md); do not infer traffic protection from a label alone. The userspace backend needs Android VPN permission and can own one active tunnel. Kernel behavior requires root and available kernel support; multiple-tunnel behavior also depends on existing settings.

Current userspace source protects native sockets at creation/rebind and, with an explicit nonzero ListenPort, makes one best-effort one-byte zero datagram attempt before each outgoing initiation on the same socket. Absent/zero ListenPort disables warm-up; endpoint-free profiles remain valid. It preserves the configured port and WireGuard protocol. Protection failure prevents socket publication; interruption or service destruction aborts activation, and endpoint resolution can independently fail startup. See [the activation contract](backend-contracts.md#wireguard-configuration-and-tunnel-state) and [native warm-up adoption](#native-warm-up-experiment). The separate Java activation preflight and late native protection remain retained baseline behavior only. PR #25's lifecycle/interruption evidence keeps its original scope; repeated errors still need diagnosis rather than blind toggles.

In retained baseline logs, `UDP preflight sent` records local send completion, not an endpoint acknowledgment or DPI protection. Preflight leaves the native WireGuard packet format unchanged. If a tunnel later loses traffic or repeats unanswered handshakes, stop load tests and retain the actual build, profile/port state and scoped logs before attributing a cause. Do not repeatedly probe a path reported blocked. A port change during recovery is a different profile/flow, not evidence that an APK or preflight fix succeeded; preserve deliberate user edits. See the [G4 incident and verification limits](reviews/2026-10-07-g4-preflight-investigation.md).

Check whether the Wi-Fi router already uses VPN when diagnosing connectivity. App-off traffic can still use the router VPN, and app-on traffic can traverse both tunnels. Use an authorized cellular path with Wi-Fi disabled or Wi-Fi without that router VPN for a clean connectivity check; record the actual path and any mobile-data limit. The [repeated network record](reviews/2026-10-07-g4-network-baselines.md) separates router-only/nested observations from cellular evidence. Successful traffic proves that exchange, not preflight effectiveness or future DPI protection.

File/ZIP importing settles valid entries before one final result and reports partial success for invalid or duplicate entries. QR image retries reopen input and recycle decoded bitmaps; exhausted allocation pressure reports an import error. Cancelling those operations does not produce failure/success feedback. These local source/JVM repairs under #22 do not prove device/provider behavior; [contracts](backend-contracts.md#import-ordering-and-export) describes the exact boundaries.

Known import/edit defects pending C8 include invalid-name dialog dismissal and replacement-length handling. Abbreviated displayed keys also require a full-key copy fix. Until repaired, inspect an exported profile when a copied key is unusable; do not paste a displayed ellipsis as a WireGuard key.

ZIP export restores its control after loading, acquisition or write failure and cancellation. The saver closes and attempts to remove an owned incomplete output; rejected or zero-result cleanup stays attached to the primary error. Check Downloads after failure and remove any incomplete private export through your file manager. A cancelled operation can still leave a complete export if cancellation arrives after writing; it does not report success. Same-name export overwrites the previous copy and does not restore it after failure. See [the export contract](backend-contracts.md#import-ordering-and-export) and [synthetic verification limits](development.md#downloads-output-ownership--2026-10-07); actual storage-provider acceptance remains in G4.

## App-data transfer

Sensitive exports and private-key reveal use Android's configured biometrics or PIN/password/pattern. Complete the system prompt; cancelling prevents the sensitive action. When Android reports no configured authentication, the existing no-lock behavior permits the action without a prompt. Authentication errors or unavailable service/hardware do not authorize it; retry after resolving the system-authentication problem.

Settings → Export app data creates a new private ZIP in Downloads after the existing administrator and biometric/device-credential gates. It includes tunnel profiles, selected settings and saved VPS connection/display records. It works with no tunnel profiles. The archive is unencrypted and contains private keys/PSKs; keep it out of Git, issues and shared evidence. Older same-name files are not overwritten by this action. Existing Export tunnels remains a profiles-only ZIP.

Use Settings → Import app data to choose the full ZIP through Android's document picker. Review the confirmation: preferences may enable remote control or restore on boot. Confirmed import prevalidates profiles and current fleet records, skips identical destination records, and rejects a different record with an existing tunnel name or server ID. It preserves unrelated records and existing active tunnel state; newly imported profiles remain off. Missing settings leave destination values unchanged. Ordinary tunnel ZIP import redirects full-transfer archives to this action instead of claiming profiles-only success. Cancelling the picker/confirmation changes nothing.

Transfer excludes kernel backend selection, saved active-tunnel intent, tile membership and Android permissions/always-on/lockdown policy. Set those up separately on a new installation. Retired updater metadata remains excluded and inert under [update policy](#app-updates). Historical VPS health/sync values are copied as stored observations, not refreshed connectivity. No SSH credentials are stored or transferred. A corrupt source/destination fleet payload blocks transfer; investigate it before retrying instead of discarding it.

If admitted import fails, it attempts to remove only the new profiles it created. A recovery warning means some new profiles remain in the tunnel list, off; inspect them before retrying. Before creating files, transfer durably clears any stale destination boot-restoration markers matching the new names; this limited cleanup is retained even if later import fails. Unrelated restoration intent and existing profiles remain preserved. Cancellation after admission can leave a completed import or recovered batch without success feedback. Process death/power loss can interrupt the separate profile-file and settings commits; inspect both stores before treating a retry as complete. [The contract](backend-contracts.md#full-app-data-transfer) defines validation, sequencing and bounds.

The maintainer approved settings/fleet transfer for [#71](https://github.com/novakin/vpn0wn-android/issues/71#issuecomment-6086430555) on 2026-10-09 (Europe/Paris). This slice retains the legacy installed ID. [Synthetic AVD acceptance](reviews/2026-10-09-app-data-transfer-acceptance.md) records the authorized debug APK installation, native PIN/cancellation/export, document-picker import, persistent readback and scoped layout checks. Physical biometric/provider/accessibility and complete migration gates remain open. A signer-compatible exporter update must reach the old installation before a new `com.vpn0wn.android` app can import its archive; separate sandboxes and `allowBackup=false` prevent direct inheritance. Preserve the old installation and data until authorized old/new-app acceptance and rollback are verified. No renamed release or permission migration is established.

## Home selection and deletion

Long-press a tunnel card to select it. Tap cards to toggle selection, use Select all for the current inventory, and Close or Back to leave selection. Zero selected remains a selection mode with Delete disabled. Add and per-row tunnel switches return on exit.

Delete opens a confirmation listing the selected profiles and warning that active/changing tunnels will be stopped. Cancellation makes no deletion. Rotation/view recreation dismisses confirmation; inspect the restored selection and confirm again. Confirmed deletes settle through the manager one at a time. Failures retain surviving profiles and selection; feedback reports observed removed/remaining counts and the first error. Back during deletion cancels the remaining work, but an already admitted delete can finish before cancellation is reported. Deletion has no undo; keep an authorized export/QR backup when needed. Source recovery does not close [#36 physical acceptance](https://github.com/novakin/vpn0wn-android/issues/36).

## Permissions and backend changes

On Android 13+, Settings offers Add tile after its stored membership state loads without confirmed membership. A confirmed Add/already-added result or manual tile-add notification hides that row across ordinary service/view recreation and subsequent app starts after the write commits. Actual tile removal makes setup available again. A tile installed before confirmation recording began retains the native idempotent Add fallback; an already-installed tile does not require another native dialog. Setup stays hidden while confirmation cannot be read and reloads when Settings resumes or reopens. Cancel and reported request failures leave setup available with existing error feedback. Service destruction alone does not remove the tile. Persistence failure or termination before commit can prevent retained confirmation. [Repaired-APK API 36 checks](reviews/2026-10-09-g4-private-native-acceptance.md#tile-membership-repair-acceptance--2026-10-09) verify native membership, cancellation, independent callbacks and reopening; physical tile toggling, accessibility and broader #34/#52 acceptance retain their own gates.

VPN permission, camera access and document/export handling depend on the selected action and Android version. Grant permissions for the requested workflow and verify the resulting action. Denial/cancellation is not success.

Switching the kernel/backend preference drains earlier transitions and shuts down active tunnels before committing the setting and restarting. New mutations are rejected between commit and restart. Failed shutdown/restart restores the previous preference and usable control; already-stopped tunnels can remain down with profiles intact. Failed preference rollback keeps the admission reservation and needs diagnosis. PR #25 merged these repairs. #15 serializes whole root/kernel transitions; real device/kernel proof remains separate. Retain sanitized evidence after failure and verify the selected backend after restart. Never delete a profile merely to diagnose an unresolved transition.

## Android system VPN Settings

For the userspace backend, open the system VPN action in Settings → Connection. Android VPN Settings owns Always-on VPN and “Block connections without VPN”; select this app and configure the available system controls there. Tunnl only opens that screen and observes this app's flags. It cannot enable these policies through an app preference. Return to Tunnl Settings to refresh the summary; observation does not start a service or request VPN permission.

| Runtime or restriction | Action and observed status |
| --- | --- |
| Go userspace, API 24–28 | Open Android VPN Settings when available and permitted. Public flag queries are unavailable; inspect the system screen. |
| Go userspace, API 29+ with an available service reference | Show this app's observed always-on/block-without-VPN flags. |
| Go userspace, API 29+ with missing or failed service access | Show unknown/unavailable status or a denied-read explanation. Missing access is never treated as flags off or protection enabled. |
| WgQuick kernel/root | Explain that this userspace system-policy path is unsupported and disable the action. Use the existing explicit backend restart action to change backend. |
| `UserManager.DISALLOW_CONFIG_VPN` | Disable the action and explain the administrator restriction while retaining the separate observation summary. A restriction does not establish protection. |
| Missing or denied Settings activity | Report unavailable or denied access through foreground feedback; no policy change is claimed. |

Flags describe this app's Android policy, not another VPN package, authenticated traffic, Internet reachability or leak-free behavior. An inconsistent always-on-off/block-on pair is unknown. Enabled flags are not an ONLINE/protected guarantee. Android lockdown can block apps excluded from the VPN; do not add app/LAN bypasses or silently widen routes to restore connectivity. Preserve deliberate AllowedIPs, IPv4/IPv6, included/excluded-app and LAN settings. Offline/captive networks do not authorize disabling policy. See [observation and pending policy contracts](backend-contracts.md#android-system-vpn-policy-observation).

The [Android VPN guide](https://developer.android.com/develop/connectivity/vpn) owns setup and lockdown behavior. [`ACTION_VPN_SETTINGS`](https://developer.android.com/reference/android/provider/Settings#ACTION_VPN_SETTINGS) is available from API 24, but a matching activity is not guaranteed. [`isAlwaysOn`](https://developer.android.com/reference/android/net/VpnService#isAlwaysOn()) and [`isLockdownEnabled`](https://developer.android.com/reference/android/net/VpnService#isLockdownEnabled()) begin at API 29; [`DISALLOW_CONFIG_VPN`](https://developer.android.com/reference/android/os/UserManager#DISALLOW_CONFIG_VPN) describes administrator restrictions. OEM/profile controls can differ even without that restriction.

This is the setup/status slice of [#75](https://github.com/novakin/vpn0wn-android/issues/75). [Scoped private API 36 acceptance](reviews/2026-10-10-private-avd-policy-acceptance.md) verifies native flag changes, foreground refresh, rendered output and restoration. Endpoint bootstrap DNS with [#73](https://github.com/novakin/vpn0wn-android/issues/73), manual/always-on arbitration with [#74](https://github.com/novakin/vpn0wn-android/issues/74), physical/conditional environments and packet-leak acceptance remain open. The [QA boundary](qa-test-plan.md#android-system-vpn-policy-acceptance) requires separate authorized proof before making leak-protection claims.

## Diagnostics and evidence

The log viewer opens with the latest 500 logcat rows. Refresh clears retained rows and starts a fresh 500-row tail; an ended/failed stream retries after one second with 50 rows, which can repeat recent entries. Batches flush at 4,000 rows or a 500ms deadline from their first pending row, without requiring more input; scheduler/Main contention can delay display. LIVE/PAUSED controls scrolling, not collection. Filters retain DEBUG (V/D), INFO (I), WARN (W) and ERROR (E/A/F) semantics.

Raw and parsed buffers each retain at most 20,000 rows. Each has a 4,194,304-character budget: complete raw-row text in the raw buffer, tag plus message text in the parsed buffer; other parsed metadata is bounded by row count. Raw rows exceeding the character budget retain their prefix; an oversized continuation message retains its newest suffix. Export snapshots retained raw rows, including continuations, regardless of the active filter. It is a bounded diagnostic tail, not a complete log archive. The share URI remains temporary and is revoked after the chooser result, another share or activity destruction. Export write/close I/O failure records a fixed diagnostic; cancellation and programming defects propagate. Existing producer redaction remains; review exported metadata before sharing. [Local regression evidence](development.md#log-pipeline-recovery--2026-10-06) does not prove Android logcat, chooser/provider or rendered-screen behavior.

Use the in-app log viewer for relevant error categories and lifecycle events. A startup error, interface creation failure, service loss and lack of handshake have different causes. Record app revision, Android/backend, the triggering action and the smallest sanitized evidence.

Debug StrictMode warnings identify the responsible operation, not a VPN outage cause. [#55](reviews/2026-10-07-g4-settings-add-debug-review.md) repaired the retained baseline's untagged Java preflight socket and the Settings kernel-support disk probe on Main without disabling detection. [Candidate-device checks](reviews/2026-10-07-g4-candidate-device-review.md) observed preflight/startup and Settings opening without those warnings on that Pixel 10a build; these historical checks do not certify the later native socket owner's accounting. Separate resource-ID-zero messages led to a [Settings source repair and candidate confirmation](reviews/2026-10-07-settings-resource-id-review.md): native preference roots now use `View.NO_ID` instead of AndroidX's default zero. The authorized `5fa07cd0` candidate showed zero errors in three Settings openings and landscape recreation, compared with nine on the preceding candidate. The precise capture service and remaining #34/#52 acceptance are unverified. Do not infer that these warnings prove DPI blocking or justify changing a working profile.

Never attach private keys, PSKs, passwords or a full generated/backup config to an issue. C1 removes raw root-shell command/stdout/stderr logging, provisioning exit-failure payloads, malformed JSON payloads/parser causes and cleanup exception payloads. Internal command results still carry authorized output; do not stringify them into diagnostics. Historical log buffers and exported files may contain secret-bearing output. Review those logs before sharing; this fix does not sanitize previously written data or establish that every transport/server message is safe.

PR #25 prevents delayed detail config/statistics from updating another selection or a destroyed view. The C7 follow-up makes a fresh idle statistics snapshot show zero and clears the rate baseline when statistics disappears. Turning a tunnel off renders the pending disconnect as off, with the switch disabled until settlement; a failed disconnect restores observed UP. Yellow CONNECTING remains specific to activation/handshake. A displayed nonzero rate or a recent sync alone cannot prove connectivity. See [follow-up evidence](development.md#phone-ui-and-throughput-follow-up--2026-10-06) for local verification and device limits.

Peer detail now shows separate cumulative RX/TX byte totals; these are not transfer rates. Missing/zero snapshots hide the transfer row, and missing/zero handshake hides its row independently. Observed DOWN clears both without waiting for another backend fetch. Values use native localized byte units and retain tap-to-copy. [Add/peer evidence](development.md#add-sheet-and-peer-presentation-recovery--2026-10-06) covers delayed selection, disconnect, failure and destruction locally; live VPN/system-bar acceptance remains separate.

A peer's authentication proves neither other peers nor Internet reachability; idle/Doze alone produces no failure. Active diagnostics clear on DOWN/replacement. Detail peer cards now present the latest recorded handshake event, observed numeric endpoint and address family in default/French text. Observations unavailable means diagnostics cannot currently be presented, including kernel/DOWN or missing state; no handshake event observed means an available userspace map has no event for that configured peer. Ordinary initiation, protocol retry, successful local send, send failure, authentication and retry exhaustion remain distinct historical facts. Unknown endpoint/family shows `—`; the saved hostname is not substituted as an observed address. The rows do not report current connection health, test Internet access or provide recovery actions. This partial presentation adds no relative event ages, recovery counts, DNS, backend mutation or polling. A separate source slice implements a retained-TUN userspace primitive, `GoBackend.rebind(Tunnel)`, under the [native lock/cancellation decision](architecture.md#handshake-observations-follow-native-protocol-and-activation-owners--2026-10-09). It adds no app control or automatic recovery trigger. Rebind retains the captured activation's TUN, configured port, peers and handshake session, without DNS or endpoint/config rewriting. Automatic-port warm-up intent remains unchanged. Inactive, busy, unavailable or retired/replaced activation returns false; manual DOWN and replacement prevent old recovery from reviving it. A true result means native transport rebind completed for the still-current activation, not that traffic or reachability recovered. Kernel rebind remains unsupported.

Protection/open failure surfaces as an I/O failure and can leave the retained TUN/activation with unavailable transport. Do not infer healthy UP from retained ownership. An unexpected JNI callback exception remains terminal under the existing context contract. An already interrupted caller never enters native rebind; interruption after admission is reported after native work settles and may follow socket replacement. The interruption flag and activation context remain preserved. See [the rebind contract](backend-contracts.md#retained-tun-userspace-rebind--73) before adding callers or interpreting outcomes. The current PR acceptance record owns exact-head review, required checks, publication and delivery state. [Rooted Android acceptance](reviews/2026-10-10-native-rebind-acceptance.md) records protected socket replacement with retained TUN/session, synthetic authenticated HTTP traffic, debugger-injected protection failure/retry and actual Android service destruction followed by fresh activation. Original settings/profile/VPN state and owned fixture resources were restored. Actual OS protection denial, phone interruption/cancellation/concurrent races, network handover, IPv6 traffic and packet acceptance remain open under #73.

Higher-level recovery must preserve manual UP/DOWN/toggle intent, saved hostnames/settings, unrelated peers and explicit ListenPort. Restoration/refresh observations are not manual overrides; #74's automation must classify user actions at manager admission.

Bootstrap is fail closed: recovery performs no outside-tunnel hostname DNS under Android lockdown, and unknown protection policy grants no exception. These slices neither change existing startup resolution nor approve outside-tunnel DNS. Rebind uses current numeric transport endpoints without rewriting a saved hostname profile. #75's setup/status contract and packet/leak proof remain separate; recoverable state or a setup label cannot prove protection. Any later permitted hostname-resolution policy must be explicit and reconciled with #75 before adding resolver/network behavior.

### Proposed bounded pilot and limits — #73

The [recommended contract](backend-contracts.md#proposed-bounded-automatic-recovery--73) is independently ultra-reviewed planning, not active recovery or new runtime/API approval. It proposes userspace recovery only after a fresh native exhausted cycle with a known current numeric endpoint. Its finite defaults still need maintainer selection before implementation. Observation and manual library rebind remain the delivered behavior; no automatic controller or recovery readout is added by this documentation.

A qualifying peer would replace transport shared by every peer, including healthy and endpoint-free peers. Only the trigger peer may receive the application's at-most-one initiation request; actual initiation or authentication is not guaranteed. Protected socket readiness is not recovered Internet/DNS access. A failed shared rebind can leave the retained activation without transport; old authentication facts and configured UP cannot override that failure. With no new eligible cycle, manual reconnect may be the only remaining path, even when budget remains.

The proposed activation budget, dropped early triggers and one bounded busy deferral are specified in the contract. Ambiguous/context-terminal settlement disables further automatic work until explicit fresh activation. Known deep Doze suppresses admission without a wake lock or wake queue; an idle exhausted peer may await later traffic/keepalive or manual reconnect. Wake, old timestamps and network churn create no failure or recovery promise.

Manual DOWN/reconnect, config/name/delete and backend changes retire recovery work at manager admission; recovery cannot bring a tunnel UP or write restoration intent. Existing boot/system always-on restoration remains unchanged. #74 still owns manual-versus-always-on/automation precedence. The pilot adds no outside-tunnel DNS, hostname/family rewrite, routing/exclusion change or protection bypass, including unknown Android policy. Full hostname/handover and #75 packet/leak acceptance remain open under the existing bootstrap boundary. [Future controls](qa-test-plan.md#proposed-recovery-controls--73) are required before claiming implemented or device-verified recovery.

## Provisioning mutation recovery

Read [script ownership and recovery](../third_party/wireguard-install/tunnl/README.md#ownership-locking-and-recovery) before an authorized server mutation. `--force` permits replacement of owned config only. Installation stops an old running unit before replacing its config/hooks. Uninstall backs up owned config before stopping/deleting, preserves global forwarding and refuses package purge while another config/live interface exists.

On mutation failure, inspect `recovery`. `unchanged` means no config/runtime mutation required restoration; `restored` means observed disk/native runtime recovery completed, plus service-state recovery for install/uninstall. Peer recovery does not snapshot or verify prior systemd unit state. Neither result promises reversal of attempted package changes or global forwarding enable. `incomplete` means inspect the retained private `recoveryPath` and any `artifact` backup before retrying. Backup/runtime files and revoke archives contain private keys/PSKs: keep permissions private and never attach contents to issues.

Success may have nonempty `cleanupPath` when committed behavior succeeded but private snapshot cleanup did not. Inspect/remove that residue only after checking current state and its recovery value. Do not retry the completed operation solely because cleanup remained. Android result models retain cleanup metadata and failures expose safe categories/codes/recovery enums. Untrusted recovery paths and arbitrary remote messages are omitted from exceptions. Live UI presentation remains C12; an operator needs an authorized server inspection for retained paths/artifacts.

Stopped peer mutations update saved config while leaving the interface absent; they do not prove live access removal or traffic health. SIGKILL, host loss, SSH timeout or a missing response leave uncertain outcomes until disk, service and actual peer state are reconciled. External tools can bypass Tunnl locks. No source/offline result authorizes production testing.

## Disposable validation and recovery

The [QA VPS use case](qa-test-plan.md#disposable-vps-integration-use-case) documents the opt-in destructive integration harness. It requires an explicitly authorized clean disposable target, no existing `wg0.conf` or Tunnl metadata, and actual root; it may install, remove peers, uninstall/purge and reinstall WireGuard. Do not run it on a production VPN host or one with user-managed WireGuard state. It is not part of default local tests/builds.

Before an authorized operational mutation, identify owned config/runtime state and relevant backup/recovery evidence. After failure or timeout, inspect actual state before retrying: a failed connection or missing response may leave a completed remote mutation. Do not claim rollback or revocation until its postconditions are observed. C9 checks exact saved/live peer sets, running state, config/interface absence and requested package purge, with payload-free stage/category/exit diagnostics. This is [offline source proof](development.md#c9-offline-harness-postconditions--2026-10-09), not real-server or packet evidence.

Harness cleanup is admitted only after actual root and successful creation of its fresh upload directory. A failed guard/root/preexisting-artifact/directory check admits no cleanup. After upload admission, failure cleanup removes that upload only; config, backups, revoke archives and recovery artifacts survive for authorized inspection. It does not automatically uninstall or retry an uncertain mutation. Tunnl artifact removal occurs only after both cycles' uninstall postconditions pass, against metadata absent before the run. Cleanup absence is checked; cleanup failure stays visible without replacing the original failure. A failed cleanup can leave the private upload or artifacts requiring scoped operator recovery.

For a relevant change or incident, adapt the reviewed VPS change/incident structure: initial state and impact, intended scope, backup, procedure, validation, rollback/recovery result and sanitized evidence. Use this when an operational change needs it; no separate runbook framework is required for routine source edits.
