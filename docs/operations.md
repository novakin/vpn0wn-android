Use the add-tunnel flow to create a profile, import a file or scan a QR code. Existing import/config parsing owns profile validation and naming. Configs and QR payloads can contain private keys; handle them as credentials. Protect exported/downloaded copies and avoid sharing screenshots or logs containing keys.

The Add sheet presents QR first, then file/archive import, then manual creation, with localized subtitles. QR is hidden when no camera feature is available. Acknowledge or dismiss that dialog to cancel the scan; no tunnel is imported. Reopen Add/Scan to try again. The [#84 repaired-APK AVD checks](reviews/2026-10-09-g4-private-native-acceptance.md#camera-repair-acceptance--2026-10-09) verify native denial, exit, grant/retry and cancellation; physical decoding and broader #35/#52 acceptance remain separate.

Successful create/save returns to the list/detail and shows the app's dark, bordered Snackbar. Validation or persistence failure leaves the editor available for correction and retains the last successfully saved configuration. An already-completed rename is not rolled back if a later config save fails. Foreground settings launch/tile failures and app-list loading failures share this feedback style. Native Toasts remain for TV, external toggle/receiver operations, detached views and tile callbacks while Settings is no longer visible. Those contexts cannot rely on a surviving foreground app view; they are deliberate visibility fallbacks.

Review interface addresses, DNS, peer endpoints and AllowedIPs before connecting. Supported WireGuard config behavior belongs to [backend contracts](backend-contracts.md); do not infer traffic protection from a label alone. The userspace backend needs Android VPN permission and can own one active tunnel. Kernel behavior requires root and available kernel support; multiple-tunnel behavior also depends on existing settings.

Current userspace source protects native sockets at creation/rebind and, with an explicit nonzero ListenPort, makes one best-effort one-byte zero datagram attempt before each outgoing initiation on the same socket. Absent/zero ListenPort disables warm-up; endpoint-free profiles remain valid. It preserves the configured port and WireGuard protocol. Protection failure prevents socket publication; interruption or service destruction aborts activation, and endpoint resolution can independently fail startup. See [the activation contract](backend-contracts.md#wireguard-configuration-and-tunnel-state) and [native warm-up adoption](#native-warm-up-experiment). The separate Java activation preflight and late native protection remain retained baseline behavior only. PR #25's lifecycle/interruption evidence keeps its original scope; repeated errors still need diagnosis rather than blind toggles.

In retained baseline logs, `UDP preflight sent` records local send completion, not an endpoint acknowledgment or DPI protection. Preflight leaves the native WireGuard packet format unchanged. If a tunnel later loses traffic or repeats unanswered handshakes, stop load tests and retain the actual build, profile/port state and scoped logs before attributing a cause. Do not repeatedly probe a path reported blocked. A port change during recovery is a different profile/flow, not evidence that an APK or preflight fix succeeded; preserve deliberate user edits. See the [G4 incident and verification limits](reviews/2026-10-07-g4-preflight-investigation.md).

Check whether the Wi-Fi router already uses VPN when diagnosing connectivity. App-off traffic can still use the router VPN, and app-on traffic can traverse both tunnels. Use an authorized cellular path with Wi-Fi disabled or Wi-Fi without that router VPN for a clean connectivity check; record the actual path and any mobile-data limit. The [repeated network record](reviews/2026-10-07-g4-network-baselines.md) separates router-only/nested observations from cellular evidence. Successful traffic proves that exchange, not preflight effectiveness or future DPI protection.

File/ZIP importing settles valid entries before one final result and reports partial success for invalid or duplicate entries. Ordinary import permits 1 MiB per profile, 16 MiB source/expanded ZIP data, 256 attempted profiles and 512 ZIP entries; text/QR profiles share the profile allowance. Oversized input stops with a safe error; earlier valid ordinary entries can still import. Split larger ordinary archives into smaller batches. An unreadable or over-limit remainder cannot establish whether it contains the full-transfer marker. [Import contracts](backend-contracts.md#import-ordering-and-export) own exact line/byte/count and cancellation limits. QR image retries reopen input and recycle decoded bitmaps; exhausted allocation pressure reports an import error. Cancelling those operations does not produce failure/success feedback. Local source/JVM repairs under #22/#167 do not prove Android provider behavior or interrupt an already-blocked provider read.

The QR naming dialog retains the scanned profile and an editable error after an invalid/duplicate name or failed save. Correct the name or retry the save; successful creation closes the dialog. Create and the name field stay disabled while submission is pending. Cancel before submission creates nothing; cancellation after manager admission cannot promise rollback of an already admitted save.

Name and key fields support correcting one character or replacing selected text at their configured maximum lengths. Existing name/key limits and final-key padding rules still apply.

Detail interface and peer public-key values stay compact on screen; tapping either value copies its complete base64 public key. RX/TX cells continue copying their displayed values. [Scoped API-28/36 acceptance](reviews/2026-10-16-detail-public-key-copy-acceptance.md) verifies synthetic complete-key pastes and representative native feedback; physical and full accessibility proof remain separate. PR #183 owns delivery state; an older installed APK may still copy the displayed ellipsis. Never paste an ellipsis as a WireGuard key.

Export tunnels requests `vpn0wn-export.zip` in Downloads and restores its control after loading, acquisition or write failure and cancellation. The saver closes and attempts to remove an owned incomplete output; rejected or zero-result cleanup stays attached to the primary error. Check Downloads after failure and remove any incomplete private export through your file manager. A cancelled operation can still leave a complete export if cancellation arrives after writing; it does not report success. Same-name export overwrites the previous copy and does not restore it after failure. Older `wireguard-export.zip` copies remain untouched by the filename rename. See [the export contract](backend-contracts.md#import-ordering-and-export) and [synthetic verification limits](development.md#downloads-output-ownership--2026-10-07); actual storage-provider acceptance remains in G4.

## App-data transfer

Sensitive exports and private-key reveal use Android's configured biometrics or PIN/password/pattern. Complete the system prompt; cancelling prevents the sensitive action. When Android reports no configured authentication, the existing no-lock behavior permits the action without a prompt. Authentication errors or unavailable service/hardware do not authorize it; retry after resolving the system-authentication problem.

An administrator disabling configuration export also prevents new private-key/PSK reveals. Profile export and editor reveal recheck the current restriction after authentication and before sensitive output, so a pending allowed prompt cannot override a newly applied restriction. Changing the editor selection or recreating its view clears key-reveal authorization and masks the fields. Later key focus checks policy again. One native authentication prompt can remain pending per Activity, including across rotation; finish or cancel that prompt before retrying a different sensitive action. Its completion belongs to the original request and cannot authorize a replacement editor or Settings view. Completed exports or data already seen/copied cannot be recalled; remove retained private Downloads copies when policy requires it. [The scoped #166 record](reviews/2026-10-12-app-root-security-audit.md) separates mocked ownership controls from actual disposable API36 DPC/PIN checks and their limits.

Settings → Export app data creates a new private ZIP in Downloads after the existing administrator and biometric/device-credential gates. It includes tunnel profiles, selected settings and saved VPS connection/display records. It works with no tunnel profiles. The archive is unencrypted and contains private keys/PSKs; keep it out of Git, issues and shared evidence. Older same-name files are not overwritten by this action. Existing Export tunnels remains a profiles-only ZIP.

Use Settings → Import app data to choose the full ZIP through Android's document picker. Review the confirmation: preferences may enable remote control or restore on boot. Confirmed import prevalidates profiles and current fleet records, skips identical destination records, and rejects a different record with an existing tunnel name or server ID. It preserves unrelated records and existing active tunnel state; newly imported profiles remain off. Missing settings leave destination values unchanged. Ordinary tunnel ZIP import redirects full-transfer archives to this action instead of claiming profiles-only success. Cancelling the picker/confirmation changes nothing.

Transfer excludes kernel backend selection, saved active-tunnel intent, tile membership and Android permissions/always-on/lockdown policy. Set those up separately on a new installation. Retired updater metadata remains excluded and inert under [update policy](#app-updates). Historical VPS health/sync values are copied as stored observations, not refreshed connectivity. SSH credentials and host pins are excluded from transfers; the [protected storage backend](backend-contracts.md#saved-ssh-credentials--c11) is separate. Enter verified access again on the receiving installation. A corrupt source/destination fleet payload blocks transfer; investigate it before retrying instead of discarding it.

If admitted import fails, it attempts to remove only the new profiles it created. A recovery warning means some new profiles remain in the tunnel list, off; inspect them before retrying. Before creating files, transfer durably clears any stale destination boot-restoration markers matching the new names; this limited cleanup is retained even if later import fails. Unrelated restoration intent and existing profiles remain preserved. Cancellation after admission can leave a completed import or recovered batch without success feedback. Process death/power loss can interrupt the separate profile-file and settings commits; inspect both stores before treating a retry as complete. [The contract](backend-contracts.md#full-app-data-transfer) defines validation, sequencing and bounds.

The maintainer approved settings/fleet transfer for [#71](https://github.com/novakin/vpn0wn-android/issues/71#issuecomment-6086430555) on 2026-10-09 (Europe/Paris). [Legacy-ID preparation](reviews/2026-10-09-app-data-transfer-acceptance.md) covers its native PIN/cancellation/export, document-picker import, persistent readback and scoped layout checks. [The 2026-10-11 synthetic cross-app record](reviews/2026-10-11-cross-app-transfer-acceptance.md) adds an actual legacy debug app export and native new-ID import on an isolated API 36 AVD. Both pinned installations remain present; recreated apps retained two DOWN profiles, five portable settings and one saved server. Source bytes stayed unchanged. Destination nonportable preference maps were empty before and after, so populated nonportable settings remain untested. This establishes the pinned pair's transfer path, not an existing-old-installation upgrade, current-master runtime or physical/release migration. Physical biometric/provider/accessibility, recovery and complete #71 gates remain open. A signer-compatible exporter update must reach the old installation before a new `com.vpn0wn.android` app can import its archive; separate sandboxes and `allowBackup=false` prevent direct inheritance. Preserve the old installation and data until authorized migration and rollback are verified. No permission migration is established.

## Home selection and deletion

Long-press a tunnel card to select it. Tap cards to toggle selection, use Select all for the current inventory, and Close or Back to leave selection. Zero selected remains a selection mode with Delete disabled. Add and per-row tunnel switches return on exit.

Delete opens a confirmation listing the selected profiles and warning that active/changing tunnels will be stopped. Cancellation makes no deletion. Rotation/view recreation dismisses confirmation; inspect the restored selection and confirm again. Confirmed deletes settle through the manager one at a time. Failures retain surviving profiles and selection; feedback reports observed removed/remaining counts and the first error. Back during deletion cancels the remaining work, but an already admitted delete can finish before cancellation is reported. Deletion has no undo; keep an authorized export/QR backup when needed. Source recovery does not close [#36 physical acceptance](https://github.com/novakin/vpn0wn-android/issues/36).

## Permissions and backend changes

On Android 13+, Settings offers Add tile after its stored membership state loads without confirmed membership. A confirmed Add/already-added result or manual tile-add notification hides that row across ordinary service/view recreation and subsequent app starts after the write commits. Actual tile removal makes setup available again. A tile installed before confirmation recording began retains the native idempotent Add fallback; an already-installed tile does not require another native dialog. Setup stays hidden while confirmation cannot be read and reloads when Settings resumes or reopens. Cancel and reported request failures leave setup available with existing error feedback. Service destruction alone does not remove the tile. Persistence failure or termination before commit can prevent retained confirmation. [Repaired-APK API 36 checks](reviews/2026-10-09-g4-private-native-acceptance.md#tile-membership-repair-acceptance--2026-10-09) verify native membership, cancellation, independent callbacks and reopening; physical tile toggling, accessibility and broader #34/#52 acceptance retain their own gates.

VPN permission, camera access and document/export handling depend on the selected action and Android version. Grant permissions for the requested workflow and verify the resulting action. Denial/cancellation is not success.

While Android's userspace VPN consent screen is open, configuration recreation keeps the original tunnel and requested direction pending. Granting continues that request once; later selection or same-name replacement cannot receive it. Denial/cancellation restores its switch to current state for retry. A missing/denied consent activity reports an error without activation. Process death or permanent fragment removal drops pending consent and requires manual retry after inspecting state; it is not restored from a profile name. Ordinary navigation after approval keeps the accepted transition's existing Activity owner. Confirm resulting tunnel/service state and usable traffic separately. See [the #177 contract](backend-contracts.md#vpn-consent-continuation--177) and [remaining Android acceptance](qa-test-plan.md#vpn-consent-continuation-acceptance--177).

Switching the kernel/backend preference drains earlier transitions and shuts down active tunnels before committing the setting and restarting. New mutations are rejected between commit and restart. Failed shutdown/restart restores the previous preference and usable control; already-stopped tunnels can remain down with profiles intact. Failed preference rollback keeps the admission reservation and needs diagnosis. PR #25 merged these repairs. #15 serializes whole root/kernel transitions; real device/kernel proof remains separate. Retain sanitized evidence after failure and verify the selected backend after restart. Never delete a profile merely to diagnose an unresolved transition.

With the [#210 observation repair](backend-contracts.md#failed-kernel-observation--210), failure to read the kernel inventory does not mean that tunnels stopped. The operation reports the original root/tool/I/O failure; a requested disconnect, delete or backend switch must not treat that failure as a successful shutdown. Keep the saved recovery profile. Restore root/tool availability and reopen the affected screen or app to retry; an earlier installed APK may retain the old behavior. Initial Home loading failure withholds configured-count, protection and empty-list claims, while TV and saved-selection restoration use existing error feedback. A failed initial tile lookup opens the app without toggling a tunnel. An authorized remote-control request reports expected initial I/O/root failures through its existing Toast without changing the tunnel; resend the authorized request after restoring observation availability to retry. These source and [scoped host/View controls](qa-test-plan.md#failed-kernel-observation-controls--210) add no new rooted-device or connectivity proof.

## Android system VPN Settings

For the userspace backend, open the system VPN action in Settings → Connection. Android VPN Settings owns Always-on VPN and “Block connections without VPN”; select this app and configure the available system controls there. vpn0wn only opens that screen and observes this app's flags. It cannot enable these policies through an app preference. Return to vpn0wn Settings to refresh the summary; observation does not start a service or request VPN permission.

| Runtime or restriction | Action and observed status |
| --- | --- |
| Go userspace, API 24–28 | Open Android VPN Settings when available and permitted. Public flag queries are unavailable; inspect the system screen. |
| Go userspace, API 29+ with an available service reference | Show this app's observed always-on/block-without-VPN flags. |
| Go userspace, API 29+ with missing or failed service access | Show unknown/unavailable status or a denied-read explanation. Missing access is never treated as flags off or protection enabled. |
| WgQuick kernel/root | Explain that this userspace system-policy path is unsupported and disable the action. Use the existing explicit backend restart action to change backend. |
| `UserManager.DISALLOW_CONFIG_VPN` | Disable the action and explain the administrator restriction while retaining the separate observation summary. A restriction does not establish protection. |
| Missing or denied Settings activity | Report unavailable or denied access through foreground feedback; no policy change is claimed. |

Flags describe this app's Android policy, not another VPN package, authenticated traffic, Internet reachability or leak-free behavior. An inconsistent always-on-off/block-on pair is unknown. Enabled flags are not an ONLINE/protected guarantee. Android lockdown can block apps excluded from the VPN; do not add app/LAN bypasses or silently widen routes to restore connectivity. Preserve deliberate AllowedIPs, IPv4/IPv6, included/excluded-app and LAN settings. Offline/captive networks do not authorize disabling policy. See [observation and pending policy contracts](backend-contracts.md#android-system-vpn-policy-observation).

The [Android VPN guide](https://developer.android.com/develop/connectivity/vpn) owns setup and lockdown behavior. [`ACTION_VPN_SETTINGS`](https://developer.android.com/reference/android/provider/Settings#ACTION_VPN_SETTINGS) is available from API 24, but a matching activity is not guaranteed. [`isAlwaysOn`](https://developer.android.com/reference/android/net/VpnService#isAlwaysOn()) and [`isLockdownEnabled`](https://developer.android.com/reference/android/net/VpnService#isLockdownEnabled()) begin at API 29; [`DISALLOW_CONFIG_VPN`](https://developer.android.com/reference/android/os/UserManager#DISALLOW_CONFIG_VPN) describes administrator restrictions. OEM/profile controls can differ even without that restriction.

This is the setup/status slice of [#75](https://github.com/novakin/vpn0wn-android/issues/75). [Scoped private API 36 acceptance](reviews/2026-10-10-private-avd-policy-acceptance.md) verifies native flag changes, foreground refresh, rendered output and restoration. Endpoint bootstrap DNS with [#73](https://github.com/novakin/vpn0wn-android/issues/73), manual/always-on arbitration with [#74](https://github.com/novakin/vpn0wn-android/issues/74), physical/conditional environments and packet-leak acceptance remain open. The [QA boundary](qa-test-plan.md#android-system-vpn-policy-acceptance) requires separate authorized proof before making leak-protection claims.

## Diagnostics and evidence

Current first-party JVM/native rows use `vpn0wn/` tags; the startup header identifies `vpn0wn/<version>` and retains Android/device/build metadata. Legacy `WireGuard/` rows and other upstream/platform tags remain visible and exportable through the existing parser and unrestricted capture. Renaming current producers does not rewrite or sanitize previously collected logs; the redaction and sharing cautions below still apply.

The log viewer opens with the latest 500 logcat rows. Refresh clears retained rows and starts a fresh 500-row tail; an ended/failed stream retries after one second with 50 rows, which can repeat recent entries. Batches flush at 4,000 rows or a 500ms deadline from their first pending row, without requiring more input; scheduler/Main contention can delay display. LIVE/PAUSED controls scrolling, not collection. Filters retain DEBUG (V/D), INFO (I), WARN (W) and ERROR (E/A/F) semantics.

Raw and parsed buffers each retain at most 20,000 rows. Each has a 4,194,304-character budget: complete raw-row text in the raw buffer, tag plus message text in the parsed buffer; other parsed metadata is bounded by row count. Raw rows exceeding the character budget retain their prefix; an oversized continuation message retains its newest suffix. Export snapshots retained raw rows, including continuations, regardless of the active filter. It is a bounded diagnostic tail, not a complete log archive. Shared log metadata names `vpn0wn-log.txt`; each localized share subject identifies vpn0wn. The share URI remains temporary and is revoked after the chooser result, another share or activity destruction. Export write/close I/O failure records a fixed diagnostic; cancellation and programming defects propagate. Existing producer redaction remains; review exported metadata before sharing. [Local regression evidence](development.md#log-pipeline-recovery--2026-10-06) does not prove Android logcat, chooser/provider or rendered-screen behavior.

Use the in-app log viewer for relevant error categories and lifecycle events. A startup error, interface creation failure, service loss and lack of handshake have different causes. Record app revision, Android/backend, the triggering action and the smallest sanitized evidence.

Debug StrictMode warnings identify the responsible operation, not a VPN outage cause. [#55](reviews/2026-10-07-g4-settings-add-debug-review.md) repaired the retained baseline's untagged Java preflight socket and the Settings kernel-support disk probe on Main without disabling detection. [Candidate-device checks](reviews/2026-10-07-g4-candidate-device-review.md) observed preflight/startup and Settings opening without those warnings on that Pixel 10a build; these historical checks do not certify the later native socket owner's accounting. Separate resource-ID-zero messages led to a [Settings source repair and candidate confirmation](reviews/2026-10-07-settings-resource-id-review.md): native preference roots now use `View.NO_ID` instead of AndroidX's default zero. The authorized `5fa07cd0` candidate showed zero errors in three Settings openings and landscape recreation, compared with nine on the preceding candidate. The precise capture service and remaining #34/#52 acceptance are unverified. Do not infer that these warnings prove DPI blocking or justify changing a working profile.

Never attach private keys, PSKs, passwords or a full generated/backup config to an issue. C1 removes raw root-shell command/stdout/stderr logging, provisioning exit-failure payloads, malformed JSON payloads/parser causes and cleanup exception payloads. Internal command results still carry authorized output; do not stringify them into diagnostics. Historical log buffers and exported files may contain secret-bearing output. Review those logs before sharing; this fix does not sanitize previously written data or establish that every transport/server message is safe.

PR #25 prevents delayed detail config/statistics from updating another selection or a destroyed view. The C7 follow-up makes a fresh idle statistics snapshot show zero and clears the rate baseline when statistics disappears. Turning a tunnel off renders the pending disconnect as off, with the switch disabled until settlement; a failed disconnect restores observed UP. Yellow CONNECTING remains specific to activation/handshake. A displayed nonzero rate or a recent sync alone cannot prove connectivity. See [follow-up evidence](development.md#phone-ui-and-throughput-follow-up--2026-10-06) for local verification and device limits.

Peer detail now shows separate cumulative RX/TX byte totals; these are not transfer rates. Missing/zero snapshots hide the transfer row, and missing/zero handshake hides its row independently. Observed DOWN clears both without waiting for another backend fetch. Values use native localized byte units and retain tap-to-copy. [Add/peer evidence](development.md#add-sheet-and-peer-presentation-recovery--2026-10-06) covers delayed selection, disconnect, failure and destruction locally; live VPN/system-bar acceptance remains separate.
