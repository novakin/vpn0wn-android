This guide describes current Android handling and known limits. The [UI roadmap](ui-redesign-roadmap.md) lists visual gaps; the [improvement plan](improvement-plan.md) tracks reliability repairs. Do not treat a rendered screen or successful command as proof of a working VPN/deployment.

## Import, edit and connect

### Optional AmneziaWG — #76

The maintainer selected the [official optional AWG engine](backend-contracts.md#optional-amneziawg-configuration-and-native-ownership--76) on 2026-10-19. [PR #302](https://github.com/novakin/vpn0wn-android/pull/302) delivered source integration; broader runtime/interoperability acceptance remains open under #76. AWG profiles need a compatible AWG server and userspace backend; ordinary WireGuard profiles and existing VPS provisioning remain WireGuard. Disable the kernel backend before starting an AWG profile. The app rejects AWG kernel activation before root/tool work; it does not convert a server or silently change protocols.

Import a complete compatible AWG profile through the existing file, archive or QR flow. Recognized AWG fields select the protocol; an otherwise default profile can explicitly use `Protocol = AmneziaWG`. Export writes the compatibility comment `# vpn0wn:protocol=AmneziaWG` and retained fields. Existing editor fields preserve imported AWG settings and display/edit peer keepalive scalar/ranges. Dedicated controls for every AWG interface field are not added; prepare those in the imported profile. The parser rejects unsafe/unsupported values with field-scoped errors. Preserve original backups before moving a profile to an older app version that lacks AWG parsing.

The AWG engine owns configured I/J handshake packets. vpn0wn's ordinary WireGuard one-byte warm-up is not layered onto AWG, including explicit ListenPort profiles. A configured packet does not establish DPI effectiveness, battery savings or server compatibility. The separate [API24 A4 probe](reviews/2026-10-19-amneziawg-native-lifecycle-acceptance.md) records passing startup/rebind/teardown and cleanup. That isolated lifecycle evidence establishes no live AWG server, Android handshake/data traffic, external-server interoperability or production readiness.

## App-data transfer

Sensitive exports and private-key reveal use Android's configured biometrics or PIN/password/pattern. Complete the system prompt; cancelling prevents the sensitive action. When Android reports no configured authentication, the existing no-lock behavior permits the action without a prompt. Authentication errors or unavailable service/hardware do not authorize it; retry after resolving the system-authentication problem.

An administrator disabling configuration export also prevents new private-key/PSK reveals. Profile export and editor reveal recheck the current restriction after authentication and before sensitive output, so a pending allowed prompt cannot override a newly applied restriction. Changing the editor selection or recreating its view clears key-reveal authorization and masks the fields. Later key focus checks policy again. One native authentication prompt can remain pending per Activity, including across rotation; finish or cancel that prompt before retrying a different sensitive action. Its completion belongs to the original request and cannot authorize a replacement editor or Settings view. Completed exports or data already seen/copied cannot be recalled; remove retained private Downloads copies when policy requires it. [The scoped #166 record](reviews/2026-10-12-app-root-security-audit.md) separates mocked ownership controls from actual disposable API36 DPC/PIN checks and their limits.

Settings → Export app data creates a new private ZIP in Downloads after the existing administrator and biometric/device-credential gates. It includes tunnel profiles, selected settings and saved VPS connection/display records. It works with no tunnel profiles. The archive is unencrypted and contains private keys/PSKs; keep it out of Git, issues and shared evidence. Older same-name files are not overwritten by this action. Existing Export tunnels remains a profiles-only ZIP.

Use Settings → Import app data to choose the full ZIP through Android's document picker. Review the confirmation: preferences may enable remote control or restore on boot. Confirmed import prevalidates profiles and current fleet records, skips identical destination records, and rejects a different record with an existing tunnel name or server ID. It preserves unrelated records and existing active tunnel state; newly imported profiles remain off. Missing settings leave destination values unchanged. Ordinary tunnel ZIP import redirects full-transfer archives to this action instead of claiming profiles-only success. Cancelling the picker/confirmation changes nothing.

Transfer excludes kernel backend selection, saved active-tunnel intent, tile membership and Android permissions/always-on/lockdown policy. Set those up separately on a new installation. Retired updater metadata remains excluded and inert under [update policy](#app-updates). Historical VPS health/sync values are copied as stored observations, not refreshed connectivity. SSH credentials and host pins are excluded from transfers; the [protected storage backend](backend-contracts.md#saved-ssh-credentials--c11) is separate. Enter verified access again on the receiving installation. A corrupt source/destination fleet payload blocks transfer; investigate it before retrying instead of discarding it.

If admitted import fails, it attempts to remove only the new profiles it created. A recovery warning means some new profiles remain in the tunnel list, off; inspect them before retrying. Before creating files, transfer durably clears any stale destination boot-restoration markers matching the new names; this limited cleanup is retained even if later import fails. Unrelated restoration intent and existing profiles remain preserved. Cancellation after admission can leave a completed import or recovered batch without success feedback. Process death/power loss can interrupt the separate profile-file and settings commits; inspect both stores before treating a retry as complete. [The contract](backend-contracts.md#full-app-data-transfer) defines validation, sequencing and bounds.

## Home selection and deletion

Long-press a tunnel card to select it. Tap cards to toggle selection, use Select all for the current inventory, and Close or Back to leave selection. Zero selected remains a selection mode with Delete disabled. Add and per-row tunnel switches return on exit.

Delete opens a confirmation listing the selected profiles and warning that active/changing tunnels will be stopped. Cancellation makes no deletion. Rotation/view recreation dismisses confirmation; inspect the restored selection and confirm again. Confirmed deletes settle through the manager one at a time. Failures retain surviving profiles and selection; feedback reports observed removed/remaining counts and the first error. Back during deletion cancels the remaining work, but an already admitted delete can finish before cancellation is reported. Deletion has no undo; keep an authorized export/QR backup when needed. Source recovery does not close [#36 physical acceptance](https://github.com/novakin/vpn0wn-android/issues/36).

## Permissions and backend changes

Disabling **Restore on boot** prevents the kernel boot receiver from activating saved tunnels, including a cold start with delayed inventory. Opening the app can still restore its saved running tunnels once per app process. Android userspace always-on remains governed by its separate system callback. An already-running kernel interface can still be observed as UP. Boot/shutdown restoration or saving remains subject to Android's bounded broadcast lifetime; host controls do not establish device reboot or timeout behavior. A background restoration error requires diagnosis or an explicit retry, not an assumption that activation succeeded.

Quick Settings preserves one absolute requested direction. An observation or save error after a completed transition reports failure and refreshes the tile without toggling again. Actual UP authorization failure may open VPN consent for the original tunnel; approval continues once, while denial/process loss drops the request. API34 overlay settings still require a new click afterward. Check the displayed/actual tunnel state before retrying a reported error. Rename similarly reports persistence failure even if its file/name change already applied; retain the current profile and inspect its current name rather than assuming rollback. [State contracts](backend-contracts.md#wireguard-configuration-and-tunnel-state) describe these boundaries.

On Android 13+, Settings offers Add tile after its stored membership state loads without confirmed membership. A confirmed Add/already-added result or manual tile-add notification hides that row across ordinary service/view recreation and subsequent app starts after the write commits. Actual tile removal makes setup available again. A tile installed before confirmation recording began retains the native idempotent Add fallback; an already-installed tile does not require another native dialog. Setup stays hidden while confirmation cannot be read and reloads when Settings resumes or reopens. Cancel and reported request failures leave setup available with existing error feedback. Service destruction alone does not remove the tile. Persistence failure or termination before commit can prevent retained confirmation. [Repaired-APK API 36 checks](reviews/2026-10-09-g4-private-native-acceptance.md#tile-membership-repair-acceptance--2026-10-09) verify native membership, cancellation, independent callbacks and reopening; physical tile toggling, accessibility and broader #34/#52 acceptance retain their own gates.

VPN permission, camera access and document/export handling depend on the selected action and Android version. Grant permissions for the requested workflow and verify the resulting action. Denial/cancellation is not success.

While Android's userspace VPN consent screen is open, configuration recreation keeps the original tunnel and requested direction pending. Granting continues that request once; later selection or same-name replacement cannot receive it. Denial/cancellation restores its switch to current state for retry. A missing/denied consent activity reports an error without activation. Process death or permanent fragment removal drops pending consent and requires manual retry after inspecting state; it is not restored from a profile name. Ordinary navigation after approval keeps the accepted transition's existing Activity owner. Confirm resulting tunnel/service state and usable traffic separately. See [the #177 contract](backend-contracts.md#vpn-consent-continuation--177) and [remaining Android acceptance](qa-test-plan.md#vpn-consent-continuation-acceptance--177).

Switching the kernel/backend preference drains earlier transitions and shuts down active tunnels before committing the setting and restarting. New mutations are rejected between commit and restart. Failed shutdown/restart restores the previous preference and usable control; already-stopped tunnels can remain down with profiles intact. Failed preference rollback keeps the admission reservation and needs diagnosis. PR #25 merged these repairs. #15 serializes whole root/kernel transitions; real device/kernel proof remains separate. Retain sanitized evidence after failure and verify the selected backend after restart. Never delete a profile merely to diagnose an unresolved transition.

With the [#210 observation repair](backend-contracts.md#failed-kernel-observation--210), failure to read the kernel inventory does not mean that tunnels stopped. The operation reports the original root/tool/I/O failure; a requested disconnect, delete or backend switch must not treat that failure as a successful shutdown. Keep the saved recovery profile. Restore root/tool availability and reopen the affected screen or app to retry; an earlier installed APK may retain the old behavior. Initial Home loading failure withholds configured-count, protection and empty-list claims, while TV and saved-selection restoration use existing error feedback. An authorized remote-control request reports expected initial I/O/root failures through its existing Toast without changing the tunnel; resend the authorized request after restoring observation availability to retry. These source and [scoped host/View controls](qa-test-plan.md#failed-kernel-observation-controls--210) add no new rooted-device or connectivity proof.

## Android system VPN Settings

For the userspace backend, open the system VPN action in Settings → Connection. Android VPN Settings owns Always-on VPN and “Block connections without VPN”; select this app and configure the available system controls there. vpn0wn only opens that screen and observes this app's flags. It cannot enable these policies through an app preference. Return to vpn0wn Settings to refresh the summary; observation does not start a service or request VPN permission.

| Runtime or restriction | Action and observed status |
| --- | --- |
| Go userspace, API 24–28 | Open Android VPN Settings when available and permitted. Public flag queries are unavailable; inspect the system screen. |
| Go userspace, API 29+ with an available service reference | Show this app's observed always-on/block-without-VPN flags. |
| Go userspace, API 29+ with missing or failed service access | Show unknown/unavailable status or a denied-read explanation. Missing access is never treated as flags off or protection enabled. |
| WgQuick kernel/root | Explain that this userspace system-policy path is unsupported and disable the action. Use the existing explicit backend restart action to change backend. |
| `UserManager.DISALLOW_CONFIG_VPN` | Disable the action and explain the administrator restriction while retaining the separate observation summary. A restriction does not establish protection. |
| Missing or denied Settings activity | Report unavailable or denied access through foreground feedback; no policy change is claimed. |

Flags describe this app's Android policy, not another VPN package, authenticated traffic, Internet reachability or leak-free behavior. An inconsistent always-on-off/block-on pair is unknown. Enabled flags are not an ONLINE/protected guarantee. Android lockdown can block apps excluded from the VPN; do not add app/LAN bypasses or silently widen routes to restore connectivity. Preserve deliberate AllowedIPs, IPv4/IPv6, included/excluded-app and LAN settings. Offline/captive networks do not authorize disabling policy. See [observation and pending policy contracts](backend-contracts.md#android-system-vpn-policy-observation).

The [Android VPN guide](https://developer.android.com/develop/connectivity/vpn) owns setup and lockdown behavior. [`ACTION_VPN_SETTINGS`](https://developer.android.com/reference/android/provider/Settings#ACTION_VPN_SETTINGS) is available from API 24, but a matching activity is not guaranteed. [`isAlwaysOn`](https://developer.android.com/reference/android/net/VpnService#isAlwaysOn()) and [`isLockdownEnabled`](https://developer.android.com/reference/android/net/VpnService#isLockdownEnabled()) begin at API 29; [`DISALLOW_CONFIG_VPN`](https://developer.android.com/reference/android/os/UserManager#DISALLOW_CONFIG_VPN) describes administrator restrictions. OEM/profile controls can differ even without that restriction.

This is the setup/status slice of [#75](https://github.com/novakin/vpn0wn-android/issues/75). [Scoped private API 36 acceptance](reviews/2026-10-10-private-avd-policy-acceptance.md) verifies native flag changes, foreground refresh, rendered output and restoration. Endpoint bootstrap DNS with [#73](https://github.com/novakin/vpn0wn-android/issues/73), manual/always-on arbitration with [#74](https://github.com/novakin/vpn0wn-android/issues/74), physical/conditional environments and packet-leak acceptance remain open. ## Planned network automation — #74

**First source slice delivered; wider installed/release acceptance pending.** [#74](https://github.com/novakin/vpn0wn-android/issues/74) remains open. The [isolated API28 native A7 record](reviews/2026-10-19-network-automation-native-acceptance.md) accepts named startup/Disable/rebind/refusal/Resume and cleanup controls. The separate [API36 Resume/Stop record](reviews/2026-10-19-network-automation-native-acceptance.md#api36-settings-resume-and-stop-acknowledgement--2026-10-19) observes real Settings/service Resume, durable acknowledgement and newer-Stop pause using Android's documented `cmd activity stop-app` simulation; Task Manager UI operation, force-stop and Disable remain distinct. These source controls and the synthetic debug cohorts establish no shipping-APK availability or wider platform/routing/UI acceptance.

Settings retains native action rows rather than a persisted switch. Choose **Default tunnel** explicitly from supported userspace profiles, including hostnames in the [selected-network extension](backend-contracts.md#selected-network-hostname-recovery--7374), then **Enable network automation**. Enable prepares existing VPN consent and contextually asks notification permission on API33+; notification denial does not itself prohibit a legal foreground monitor. Existing kernel/multiple-tunnel modes are outside this slice; Settings explains the single-userspace prerequisite and disables Enable in those modes. Enable rejects a missing/incompatible default or another running tunnel instead of substituting a profile.

If import or prior kernel use left the multiple-tunnel setting enabled, Go userspace Settings shows **Saved multiple-tunnel mode** as an explicit OFF repair. Its checked value represents the saved setting, not simultaneous userspace support. Turn it off to satisfy the automation prerequisite; the row hides after the save succeeds. Kernel Settings keeps its normal multiple-tunnel control. Unavailable preference reads retain the last display and disable the repair; reopening Settings can load the value again. No setting is cleared silently, and this repair changes no backend or active tunnel.

**Network automation** status separates disabled, enabled/inactive, monitoring, waiting for a public network, public-N bound, manual hold, user-Stop pause, unresolved binding, failed/uncertain work, finishing/unsaved hand-back and proved same-live Android handling. Monitoring and bound status establish no VPN/Internet health. **Resume monitoring** restarts eligible monitoring or acknowledges Stop within the existing episode; manual holds and failed-attempt suppression remain. A fresh explicit Disable→Enable creates a new episode after settlement, rechecking the current actual default/config without old receipt authority.

An already active monitor's Resume keeps its current hold/failure readout; it does not briefly claim successful monitoring or retry the inhibited action. A completed numeric manual UP on another profile retains that exact live profile and hold while its sockets follow public-network selection/loss. An absent/replaced/fenced non-default manual owner is never automatically started, and an unused default's unavailable binding does not freeze the held live profile. Existing enabled restoration of the completed/resolved default still requires its committed running intent after recreation. Do not retry the completed operation solely because cleanup remained. Android result models retain cleanup metadata and failures expose safe categories/codes/recovery enums. Untrusted recovery paths and arbitrary remote messages are omitted from exceptions. Confirmed installation now renders fixed recovery/cleanup messages; an operator still needs an authorized server inspection for retained paths/artifacts.

Stopped peer mutations update saved config while leaving the interface absent; they do not prove live access removal or traffic health. SIGKILL, host loss, SSH timeout or a missing response leave uncertain outcomes until disk, service and actual peer state are reconciled. External tools can bypass vpn0wn locks. No source/offline result authorizes production testing.

## Disposable validation and recovery

The [QA VPS use case](qa-test-plan.md#disposable-vps-integration-use-case) documents the opt-in destructive integration harness. It requires an explicitly authorized clean disposable target, no existing `wg0.conf` or Tunnl metadata, and actual root; it may install, remove peers, uninstall/purge and reinstall WireGuard. Do not run it on a production VPN host or one with user-managed WireGuard state. It is not part of default local tests/builds.

Before an authorized operational mutation, identify owned config/runtime state and relevant backup/recovery evidence. After failure or timeout, inspect actual state before retrying: a failed connection or missing response may leave a completed remote mutation. Do not claim rollback or revocation until its postconditions are observed. C9 checks exact saved/live peer sets, running state, config/interface absence and requested package purge, with payload-free stage/category/exit diagnostics. This is [offline source proof](development.md#c9-offline-harness-postconditions--2026-10-09), not real-server or packet evidence.

Harness cleanup is admitted only after actual root and successful creation of its fresh upload directory. A failed guard/root/preexisting-artifact/directory check admits no cleanup. After upload admission, failure cleanup removes that upload only; config, backups, revoke archives and recovery artifacts survive for authorized inspection. It does not automatically uninstall or retry an uncertain mutation. Tunnl artifact removal occurs only after both cycles' uninstall postconditions pass, against metadata absent before the run. Cleanup absence is checked; cleanup failure stays visible without replacing the original failure. A failed cleanup can leave the private upload or artifacts requiring scoped operator recovery.

For a relevant change or incident, adapt the reviewed VPS change/incident structure: initial state and impact, intended scope, backup, procedure, validation, rollback/recovery result and sanitized evidence. Use this when an operational change needs it; no separate runbook framework is required for routine source edits.
