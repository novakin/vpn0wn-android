These declared versions define the check/build recipe, not a tested device matrix or byte-identical APK guarantee.

Native builds use the [CMake configuration](../tunnel/tools/CMakeLists.txt) and [Go Makefile](../tunnel/tools/libwg-go/Makefile): host C compiler, NDK make, POSIX shell/tools, `flock`, `curl`, `tar`, `patch` and SHA256 verification. The Makefile downloads pinned Go 1.26.9 and applies the existing boottime runtime patch. The module declares Go 1.26.0 with `x/crypto v0.58.0`, `x/net v0.61.0` and `x/sys v0.49.0`; the WireGuard pseudo-version is unchanged. Downloading Gradle/dependencies and Go needs network access on a cold cache. macOS needs [flock](https://github.com/discoteq/flock) and the required command-line tools. Use a configured Linux/macOS or WSL Linux toolchain. The clean repository tracks `gradlew`, not `gradlew.bat`; native Windows execution is not established by opening Android Studio. A Windows SDK path is not necessarily usable inside WSL; check the environment that runs Gradle before diagnosing build failures.

Runtime preparation tracks the compiler archive, checked-in boottime patch and Makefile as inputs. A changed input replaces only `BUILDDIR/go-<version>` under a sibling preparation lock, rechecks the archive's pinned SHA256 and writes `.prepared` only after extraction and patching succeed. Concurrent preparation rechecks freshness inside the lock; unchanged inputs retain the generated tree and Go's package cache. Failure leaves no accepted marker, and the next attempt starts from the verified archive rather than patching partial output. This lock serializes preparation; do not edit preparation inputs while another invocation is already compiling with that generated toolchain.

Run `python3 -m unittest discover -s scripts/tests -p 'test_go_runtime_preparation.py'` for disposable host controls using the production Makefile with synthetic archives and patches. The eight controls cover patch/Makefile/archive invalidation, unchanged reuse, checksum rejection, extraction/patch failure recovery, owned-tree preservation and concurrent preparation. CI runs them without an APK build. They establish the preparation recipe's behavior, not a new real-toolchain, Android ABI, APK or device result.

Each CMake native invocation calls cached `go build`, even when the output library exists. Go owns dependency evaluation for changed Go/JNI/helper inputs; an unchanged build can reuse its compiled packages. In the native transport implementation, `cmd/wireguard-overlay` validates the exact pinned WireGuard version, rejects replacements in the original module and patches `device/device.go`, `device/peer.go`, `device/noise-protocol.go`, `device/uapi.go`, `device/send.go`, `device/timers.go` and `conn/boundif_android.go`. Those patches preserve requested-port/rebind cleanup, explicit ListenPort intent and unavailable-family descriptor guards, and expose protocol-owned handshake observations and the [retained-TUN rebind primitive](backend-contracts.md#retained-tun-userspace-rebind--73), plus [expected-session exhausted-cycle admission](backend-contracts.md#expected-session-exhausted-cycle-recovery-primitive--73). When module metadata has no extracted source directory, the helper downloads that validated pin before reading it.

Go 1.26 rejects overlays beneath `GOMODCACHE`. The helper refreshes an owned `wireguard` source stage under its generated output, copies the main `go.mod`/`go.sum` there and creates an output-only relative WireGuard replacement through `go mod edit`. Make invokes the helper on the host platform under `BUILDDIR/wireguard-overlay/<ABI>`, then passes that generated `go.mod` with `-modfile` alongside `-overlay`. Cached upstream source and tracked module files are unchanged; a cold build may download the validated module. The generated replacement retains the required upstream version but omits its original embedded dependency sum from Go build metadata. Source sums, verified downloads and retained input/source receipts own that provenance; this verification explicitly ran `go mod verify`, while ordinary builds do not run it on every invocation. [The maintenance record](reviews/2026-10-17-native-toolchain-maintenance.md) owns executed proof and remaining limits, including scoped separate-package API24 x86_64 loading/traffic/rebind/DOWN acceptance and the distinction between stripped packaged scan fallback and its byte-matched unstripped counterpart. This is not shipping-APK or signed-release equivalence.

The host-only `recovery_fixture.go` overlay invokes actual initiation/exhaustion owners for native handle-teardown tests without waiting through protocol timing; Android overlays exclude this fixture. Host-native race checks run with `bash tunnel/tools/libwg-go/test-host.sh`, using the same pinned/prepared Go 1.26.9 recipe, a separate generated `test-overlay/go.mod` and standard host C compiler. The former `goindex=0` override is removed because staged source lies outside the module cache's index; Go's compiled-package cache remains enabled. `BUILDDIR` and `GRADLE_USER_HOME` retain their existing meanings. The [Android workflow](../.github/workflows/android.yml) runs host tests alongside JVM/static checks; this step does not assemble an APK or compile Android native ABIs. Confirm actual CI execution/results rather than inferring them from the workflow.

From that environment, `./gradlew :ui:assembleDebug --console=plain` assembles a debug APK after setup. ### Preferences disk transactions — #270

`Application` creates the existing `settings.preferences_pb` store through `createPreferencesDataStore`. A connection-owned coroutine mutex surrounds the default AndroidX `FileStorage` connection's actual read/write scopes. Disk readers wait for an admitted write scope to settle; warm cache reads retain DataStore's existing behavior. The default provider, serializer, path, protobuf, keys and lifetime remain unchanged. The shared tunnel fixture uses the same factory and retains its existing cancellation-safe owner drain.

The pinned AndroidX 1.2.1 Android `FileStorage` uses `Files.move(REPLACE_EXISTING)` without `ATOMIC_MOVE` on API 26+. [Android API 28 libcore](https://android.googlesource.com/platform/libcore/+/android-9.0.0_r61/ojluni/src/main/java/sun/nio/fs/UnixCopyFile.java#420) deletes an existing destination before renaming. A reader that captured the older cache before another write advances the version can take DataStore's unlocked disk-read path during the missing-file interval and receive empty defaults. The cache updates before final replacement, so the missing interval alone is insufficient to establish this interleaving. The guard excludes that same-connection disk-read overlap; it does not change filesystem replacement or cover independent processes/direct file access.

[#270](https://github.com/novakin/vpn0wn-android/issues/270) owns the bounded repair. [QA](qa-test-plan.md#preferences-disk-scope-controls--270) distinguishes actual storage ordering/compatibility checks from the inferred cause of the historical CI failure. Independent ultra review rejected an initial Okio-storage alternative because [AndroidX deliberately changed its default to mitigate corruption](https://developer.android.com/jetpack/androidx/releases/datastore#1.1.5), with no verified resolution of b/346197747 found in pinned 1.2.1. Retain that default provider. Do not replace immediate read assertions with polling, delay unrelated application work or suppress I/O errors. This disk-scope guard does not address the provider's failed-final-rename behavior or same-instance cache reconciliation after failed persistence; [#271](https://github.com/novakin/vpn0wn-android/issues/271) owns the separately reproduced shared-settlement boundary below. No new power-loss or cache-rollback guarantee follows.

### Gradle 9.8.1 compatibility and upgrade notes

The [official Gradle matrix](https://docs.gradle.org/9.8.1/userguide/compatibility.html) supports JDK 21 within its Java 17–27 runtime range and tests Android Gradle Plugin 9.0 through 9.5.0-alpha02. [AGP 9.1 guidance](https://developer.android.com/build/releases/agp-9-1-0-release-notes) requires at least Gradle 9.3.1/JDK 17 and uses Kotlin Gradle plugin 2.2.10; [built-in Kotlin guidance](https://developer.android.com/build/migrate-to-built-in-kotlin) supports the existing same-version `com.android.legacy-kapt` plugin. Gradle's embedded Kotlin 2.4.10 compiles build scripts; it does not replace the app compiler owned by AGP. [Detekt 1.23.8's support matrix](https://detekt.dev/docs/1.23.8/introduction/compatibility/) lists Gradle 8.12.1/Kotlin 2.0.21/AGP 8.8.1/JDK 21 as its tested tooling, so that matrix alone does not establish this repository's newer combination. The full unit/static command below, including DataBinding/KAPT compilation, remains the repository compatibility gate.

The [intervening 9.4–9.8 migration notes](https://docs.gradle.org/9.8.1/userguide/upgrading_version_9.html) cover embedded Kotlin/Groovy updates, Wrapper system-property precedence, removed Problems API internals, relocated internal dependencies, Configuration Cache singleton/concurrency serialization and `Copy`/`Sync` destination compatibility. The Problems API removal affects AGP 8.x; this project already uses AGP 9.1. Existing build scripts do not import the removed/relocated internals or serialize custom concurrency state. No plugin, Java source level, SDK/NDK/CMake pin or configuration-cache policy changes accompany the wrapper update.

Gradle 9.8.1 configuration reports AGP-owned `Configuration.setVisible` and Project-object dependency-notation deprecations, scheduled for removal in Gradle 11 and 10 respectively. Detekt's `ReportingExtension.file` deprecation, scheduled for Gradle 10, was already reported by the previous 9.3.1 wrapper. The newer Kotlin DSL compiler also reports the existing `assets.srcDir` API in [the UI build script](../ui/build.gradle.kts). These remain nonfatal configuration warnings; do not suppress them or weaken checks. `--warning-mode=all` and the ignored Gradle problems report identify the owners. Future plugin/API remediation is separate unless the required compatibility gate exposes a blocker.

Regenerate tracked wrapper configuration, JAR and Unix launcher together through two official `wrapper` task passes, as [Gradle's wrapper guide](https://docs.gradle.org/9.8.1/userguide/gradle_wrapper.html#sec:upgrading_wrapper) requires for fully updated artifacts. After both passes, reapply the Unix launcher and properties file's separate [fork modification notices](license-attribution.md#fork-source-notices), which generation replaces. In Linux/WSL:

```bash

grep -n '^# Modified for vpn0wn\.$' gradlew gradle/wrapper/gradle-wrapper.properties

Keep an already correctly placed single notice; reject duplicates or misplaced notices during verification. Confirm exactly one notice per file: within the launcher's leading legal header and on the properties file's first line. Preserve the launcher's generated copyright, complete Apache text and SPDX identifier, and all generated property values, escaping and distribution checksum. These comments do not modify the wrapper JAR or add a license declaration to the properties file. Verify the distribution and JAR against [official release checksums](https://gradle.org/release-checksums/). Preserve the existing Unix-only launcher scope; generation of an optional batch launcher does not establish native Windows build support. Rollback restores all three tracked wrapper artifacts together, including their applicable notices. ## Pull requests and merge instructions

### Issue links and resolution

Use `Fixes #N` in the PR description only when merging into the default branch fulfils the issue's full acceptance boundary. Prefer GitHub's Development relationship for resolving work and verify the actual link, or disclose unavailable access. For partial delivery, historical evidence or separately required operator/settings/target proof, use `Related to #N` and `#N remains open`; manually linked Development PRs can also auto-close issues. A branch name or plain reference alone is not a formal resolving relationship.

Negation does not neutralize closing-keyword syntax: an unsafe placeholder such as `Does not fix #N` can still create a resolving relationship. Use `Related to #N; #N remains open` instead. [PR #152](https://github.com/novakin/vpn0wn-android/pull/152) exposed this trap on 2026-10-11 (Europe/Paris); replacing the negated sentence cleared the unintended relationship and kept the partial-work issue open, as recorded in [#153](https://github.com/novakin/vpn0wn-android/issues/153). Retain that observed before/after evidence; do not create a live resolving reference to test the parser.

After PR-body changes and before authorized merge, read back the actual Development relationship and issue state, and confirm acceptance and proof.
