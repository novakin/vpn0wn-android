# Architecture and maintenance boundaries

Last updated: 2026-10-19 (Europe/Paris).

[Documentation index](../README.md#project-documentation) · Reviewed 2026-10-06

Preserve the existing Android DataBinding/Fragment foundation and upstream WireGuard config/backend ownership. This guide describes current code; planned integration and repairs are identified explicitly.

## Retain two protocol engines in one native runtime — #76, 2026-10-19

**Problem:** the selected optional AWG engine introduces distinct native device/configuration types. Copying its Android wrapper would lose this app's protected-socket startup, transport capture, handle/query drain and teardown ownership. A second c-shared library would duplicate lifecycle code and introduce Go-runtime/symbol coexistence risk.

**Decision/status:** source delivered in [PR #302](https://github.com/novakin/vpn0wn-android/pull/302) on 2026-10-19; broader runtime/interoperability acceptance remains open under #76. The maintainer [selected official optional AWG](https://github.com/novakin/vpn0wn-android/issues/76#issuecomment-6259581090); retain both pinned device packages in the existing single Go runtime and select explicitly at activation. A concrete AWG `conn.Bind` bridge delegates to the existing protected UDP owner while bypassing the ordinary WG warm-up detector. A shared lifecycle interface has two real native implementations. Reuse version-checked ownership patches with explicit AWG source matches; never apply the WG overlay blindly to another module.

**Alternatives/consequences:** separate `libawg-go.so` would require distinct JNI/SONAME/build outputs and duplicate runtime proof; replacing WG with AWG would change the verified ordinary-protocol baseline. Neither is chosen. Shared transitive dependencies require a resolved-module/license review, and both ordinary WG regressions and AWG behavior must pass against the actual combined binary. The existing Go 1.26.9 toolchain meets AWG's Go 1.25 minimum; API24 remains unchanged.

**Compatibility/verification:** the [configuration contract](backend-contracts.md#optional-amneziawg-configuration-and-native-ownership--76) owns explicit protocol intent, lossless fields, allocation bounds and honest kernel refusal. The existing editor retains imported AWG fields through edits/recreation. [Combined source/ABI checks](qa-test-plan.md#optional-amneziawg-controls--76) and the [scoped API24 A4 lifecycle cohort](reviews/2026-10-19-amneziawg-native-lifecycle-acceptance.md) pass at their recorded revisions/artifacts. Android traffic/protection observation, matching-server interoperability and broader platform/release acceptance remain open; no DPI or performance claim follows from the architecture choice.

## Runtime flows

```mermaid
flowchart LR
    Views[Fragments and views] --> Manager[TunnelManager and ObservableTunnel]
    Manager --> Store[ConfigStore]
    Manager --> Backend[Backend interface]
    Backend --> Go[GoBackend and VpnService]
    Backend --> Kernel[WgQuickBackend and RootShell]

```

UI actions request model/backend changes; backend state/statistics return through observable data and bindings. Keep UI formatting separate from operation success, permission/service management and config parsing. Detail config/statistics jobs belong to the view lifecycle and guard completions by binding/selection identity. Manager admission owns state settlement; [the decision below](#tunnel-mutations-own-admission-and-settlement) describes #13's merged repairs and limits. #15's kernel transition decision is recorded below.

Peer detail rows consume nullable immutable `Statistics.PeerStats` snapshots mapped by public key. The fragment projects only a successful statistics completion for its current view, selection, resumed lifecycle and captured state; observed DOWN clears without requesting statistics. Binding helpers own localized RX/TX totals and empty/zero visibility. These view guards complement the manager's shared-cache session checks; they do not own them. The Add sheet retains native BottomSheetDialogFragment and fragment-result actions; its callback belongs to the sheet view, while existing importer/editor owners retain validation, failure and cancellation. See [source verification and device limits](development.md#add-sheet-and-peer-presentation-recovery--2026-10-06).

`View.applySafeAreaInsets` in `util/Extensions.kt` owns system-bar/display-cutout padding for MainActivity's single-/two-pane containers, TunnelCreatorActivity and SettingsActivity. The existing pure view behavior moved out of the tunnel-selection BaseActivity so Settings can reuse it without inheriting tunnel state. It clears the handled inset types for descendants while preserving IME/gesture insets. Fragments do not add the same header inset again. Settings uses PreferenceFragmentCompat with always-expanded native sections, unchanged preference keys/defaults and native action owners; eligibility filtering removes empty categories and defers the Connection header until backend/root checks finish. The editor uses a DataBinding header inside its existing fragment, matching the prototype title/context, Close and Save controls; both host activities hide their native ActionBar. Save and the retained keyboard/menu entry call the same validated persistence owner. `ObservableTunnel` retains the manager's resolved pending target for presentation, and BindingAdapters shares each rate calculation by statistics snapshot. See [presentation contracts](backend-contracts.md#persistence-and-presentation), [phone evidence](development.md#phone-ui-and-throughput-follow-up--2026-10-06) and [Settings proof/limits](development.md#settings-presentation-recovery--2026-10-06).

The Home vertical layout reserves its Add footer below a weighted scroll container. Standard Material `AppBarLayout` behavior lets the unchanged header/status scroll above the list or empty-state `NestedScrollView` in short viewports; entering or leaving selection expands the header, while count/statistics updates retain its position. Transient phone feedback reuses `Vpn0wnSnackbar` through `Snackbar.vpn0wnStyle()`, which clears the Material background tint before installing its local surface. Successful editor feedback belongs to the surviving Main/list view; Creator returns the message through the existing Android activity-result mechanism. Native Toasts remain only in the visibility contexts described in [operations](operations.md#import-edit-and-connect); no new feedback service or state model is introduced.

Import/export children belong to their operation rather than the application scope. Valid ZIP entries settle independently through the existing manager; completion feedback runs once afterward. QR decoding owns each reopened input/bitmap. Narrow error handling preserves cancellation and exposes programming defects while existing generic Backend/ConfigStore boundaries retain needed reconciliation/reporting. [Import/export contracts](backend-contracts.md#import-ordering-and-export) records failure and output-acquisition limits; no new service, parser or dependency is introduced.

For #166, `BiometricAuthenticator` owns one pending native authentication session per Activity through a retained ViewModel. AndroidX 1.1.0 shares a mutable callback between that Activity's fragments, so independent per-view request tokens alone cannot prevent an old native success being retargeted to a new request. The Activity constructor, one-session admission and immediate native-event capture preserve the original callback through rotation and queued delivery; existing sensitive-action owners still validate current policy/view/configuration before output. A fragment-local prompt, immediate slot release on view destruction or a plain Activity-keyed map would lose this retained ownership. A pending prompt must reach its native terminal event before another native action can start; permanent Activity destruction settles the caller. This changes neither configured-authentication/no-lock policy nor app storage format. Focused shared-callback controls and separately scoped native DPC/PIN evidence are linked from [the audit follow-up](reviews/2026-10-12-app-root-security-audit.md).

The [G2 performance investigation](reviews/2026-10-07-performance-source-investigation.md) traces polling/model publication, view animation and native transfer owners. Resumed/attached presentation is not necessarily uncovered: the investigated single-pane Detail left Home active, and hidden attached widgets retain animator callbacks (#47). The later [#193 navigation repair](qa-test-plan.md#detail-header-action-controls--193) hides the retained phone Home view within the Detail transaction; it does not remove that Fragment or establish a polling/energy improvement. Its historical shared-statistics gap is addressed by the separately authorized #48 source implementation described below and in [presentation contracts](backend-contracts.md#persistence-and-presentation); current change acceptance belongs in its PR. Keep native packet/config ownership and defer measured optimization selection and physical evidence to G4. Source changes do not establish energy or throughput gains.

## Boundaries and invariants

These are required maintenance invariants, not guarantees that all current owners already meet them. `VpsServerStore` uses DataStore transactions and nullable observed running health; `FileConfigStore` serializes operations and commits synced staged files through native atomic rename. PR #25 merged manager/detail/userspace lifecycle repair; #15 implements kernel transition serialization with controlled offline proof. Exact contracts and proof limits belong below and in the backend contracts.

- `.design/` supplies read-only visual intent; it does not establish runtime capability.
- Config parsers and backends preserve supported WireGuard behavior. Do not invent another parser for generated/imported profiles.
- Stores must preserve prior valid data and serialize conflicting mutations through the responsible persistence mechanism. Backend transitions must settle on success/failure/cancellation.
- Transport owns its channels/sessions, real deadlines and cancellation. A coroutine wrapper alone cannot prove cancellation of blocking library calls.
- Shell argument quoting protects shell construction; script/config validation and ownership checks protect privileged writes. Neither substitutes for the other.
- Logs/errors expose useful categories and non-secret status, not raw private config/credential payloads. Internal results may legitimately carry a generated profile; they are not safe to stringify into diagnostics.
- Revocation/install/uninstall success needs effective postconditions and recovery semantics. Recent synchronization is not running health.
- Keep [pinned upstream attribution](../third_party/wireguard-install/UPSTREAM.md). The original interactive installer is reference material, not the Android execution path.

See [backend contracts](backend-contracts.md) for known divergences and [the plan](improvement-plan.md) for repair ownership.

## Consequential decisions

### Resolve VPN hostnames through the existing selected Network — #73/#74, 2026-10-19

**Problem:** ordinary DNS can recurse through a failed VPN, while the previous recovery pilot only reused the observed numeric endpoint. The automation owner already captures and protects sockets on one public Android Network; hostname profiles were excluded from that owner.

**Decision/status:** the maintainer [selected DNS outside the tunnel only for the VPN server hostname](https://github.com/novakin/vpn0wn-android/issues/73#issuecomment-6259581441), including under lockdown. Extend existing owned startup and the exhausted-cycle recovery primitive to resolve on that captured Network. Preserve saved hostnames, peer/config fields, TUN/session, ports, warm-up and controller accounting. Extend the existing automation chooser/admission to hostname profiles; handover itself keeps its current no-DNS/no-initiation semantics. [PR #300](https://github.com/novakin/vpn0wn-android/pull/300) delivered this source after independent ultra review and passing final-head CI; installed/runtime acceptance remains open.

**Alternatives/consequences:** the public Android Network API supplies `getAllByName`; no process binding, extra resolver library, ping worker or parallel monitor is needed. App-default callbacks can identify the VPN, and Android's public NetworkCapabilities API supplies no underlying-Network getter. Arbitrary network inventory therefore cannot justify a LEGACY resolver association. That path retains existing numeric recovery and may need manual reconnect after a hostname change. Network resolution can block until Android settles; stale/interrupt/session/config/generation checks prevent its result applying after retirement. Native endpoint mutation is atomic with the existing peer/exhaustion claim and preserves the remote port; failed admitted rebind may retain the new runtime address without usable transport. The [contract](backend-contracts.md#selected-network-hostname-recovery--7374) owns exact scope and [QA](qa-test-plan.md#selected-network-hostname-recovery-controls--7374) owns execution and remaining gates. No schema/profile migration occurs.

### Select background network ownership — #74, 2026-10-18

**Problem:** ordinary VPN teardown ends its service, while network rules need an independent lifetime when the VPN is DOWN. While UP, inventory/default callbacks neither prove which public Android Network carries native sockets nor expose that Network's physical internals. Unserialized rule, manual, restoration and recovery work could also undo newer intent.

**Decision/status:** selected policy delivered through [PR #297](https://github.com/novakin/vpn0wn-android/pull/297), merged as `a7c57049`; the first source slice was subsequently delivered through [PR #298](https://github.com/novakin/vpn0wn-android/pull/298) on 2026-10-19, with [bounded API28 native A7 acceptance](reviews/2026-10-19-network-automation-native-acceptance.md). Wider #74 and release acceptance remain open. The maintainer selected [background lifetime](https://github.com/novakin/vpn0wn-android/issues/74#issuecomment-6252795356) and [full network ownership](https://github.com/novakin/vpn0wn-android/issues/74#issuecomment-6253089647), then explicitly chose [working mobile over Wi-Fi without Internet and Disable keeping VPN ON with Android handling](https://github.com/novakin/vpn0wn-android/issues/74#issuecomment-6253415194). The [published reviewed policy](https://github.com/novakin/vpn0wn-android/issues/74#issuecomment-6253599713) records independent design acceptance and its limits. This supersedes #74's original planning exclusion of a new service and the rejected validation-agnostic/retained-pin recommendations. It does not change the narrower no-service decisions for #73 recovery or #75 status. #74 remains open for supported implementation and wider acceptance.

**Ownership:** `NetworkMonitorService` is default-disabled and independent of `GoBackend.VpnService`; it owns passive callback registrations, immutable snapshots and their lifecycle. `NetworkAutomationController` uses `TunnelManager` admission for intent, restoration arbitration and settlement; `NetworkAutomationState` stores bounded configuration/episode/receipts in existing Preferences DataStore. `AutomationNetworks` ranks public candidates and `AutomationStopHistory` handles positive user-stop observations. Existing GoBackend activation/JNI/native Bind/IPC owners capture and publish each socket generation. The monitor owns no VPN/TUN/socket and cannot directly call the public manual transition API. Settings presents controls/status through its existing native preference owners; DataBinding/Fragment architecture and ordinary VPN teardown remain.

**Policy and consequences:** choose eligible public N by validated/noncaptive quality first, advisory losing preference within that tier, then transport/tie policy. Validation is platform Internet evidence, not tunnel health. Explicit Disable retires automation authority durably, then replaces bound sockets with protected unbound sockets under the same TUN/activation/runtime port; disclose the brief traffic gap. Only successful Legacy settlement restores Android handling. Failure stays disabled with truthful retained-pin/unavailable feedback and manual reconnect guidance, without automatic conversion retry or re-enable. [Backend contracts](backend-contracts.md#planned-network-automation--74) own publication, cancellation and durable/native settlement; [operations](operations.md#planned-network-automation--74) own support and permissions.

**Evidence limits:** binding pins public N, not hidden physical routing. Opaque paths support protective numeric default traffic, not physical-specific mappings, trusted OFF or manual-epoch release. Positive same-N public Wi-Fi identity is a separate gate; cellular/Ethernet labels establish no physical rule proof. Filtered `onLost`/`onAvailable` can mean only request-match changes. They, validation/advisory changes and unknown cause cannot expire an admitted manual hold, even after actual sockets move. The current filtered observer establishes no independent disconnect/new-association seam, so conservative holds may persist. Do not invent an API or weaken this limit to complete #74.

**Alternatives:** a connect-from-DOWN-only pilot cannot meet the selected while-UP scope; it was not selected. Reusing the ordinary VPN service as a dummy lifetime would change teardown/routing. Polling, probes, extra network requests, wake work, workers/alarms, a scheduler, process binding, multipath or full VPN rebuilds add unsupported behavior. Retaining a public-N pin after successful Disable contradicts the answered requirement; silently unbinding on owned handover failure is also forbidden.

**Compatibility/verification:** the delivered first slice began with numeric/endpoint-free single-userspace ownership with actual default/Enable/status/Resume/Disable source controls, startup/adoption, while-UP handover/loss and explicit hand-back. Exact Wi-Fi/physical rules, OFF rules and profile substitution are outside this slice. Enabled name/config/import mutations need durable automation fences; ordinary disabled controls/restoration add no mandatory fence/receipt writes. A later explicit Enable resolves the current default/model/config afresh and creates a new episode without inherited receipt authority. Persistence stays bounded in the existing store and out of app-data transfer. Preserve config/port/warm-up and finite #73 accounting; endpoint-only DNS is selected and implemented by the [hostname extension](#resolve-vpn-hostnames-through-the-existing-selected-network--7374-2026-10-19); AWG retains its separate delivery boundary. The 2026-10-18 independent design review was offline under historical source scope `81e88ce7`, with no installed/packet proof. [Current QA requirements and checkpoint limits](qa-test-plan.md#planned-network-automation-controls--74) distinguish source work from final-head JVM/native/static/CI, independent review and separately authorized UI/platform/packet acceptance. Revisit when a stronger public association seam, supported scope or platform policy changes; preserve earlier review limits. Battery stays last.

### Retain current local-port policy after assessment — #77, 2026-10-18

**Problem/decision; no candidate selected:** existing incident, exhaustion, loopback and port-lifecycle evidence does not diagnose a failure that a new local port would remedy. The [dated source/contract assessment](reviews/2026-10-18-local-port-recovery-assessment.md) therefore retains current behavior. This is a no-change assessment outcome, not a finding that rotation is ineffective.

**Alternatives/consequences:** adopting runtime rotation now would introduce interface-wide flow changes and possible UDP/NAT/firewall disruption without a justified target, including effects on healthy peers and fixed-port requirements. Keep explicit ListenPort, fresh native automatic selection and retained selected-port rebind semantics, profiles, remote Endpoint, warm-up and recovery/bootstrap boundaries. No source/configuration migration is needed. A later diagnosed candidate remains subject to #77's existing separate selection and authorization criteria; optional AWG remains unselected.

**Verification/status:** existing trials keep their original dates and limits; no new runtime test or rotation occurs. Final documentation-head review, parent #72 rationale and publication/issue readback remain pending. Broader #61/#73/#75/#76 and #72 stay open.

### Require caller intent for restoration and tile retry — #244/#247, 2026-10-17

Inventory initialization previously forced restoration for every application start, before a boot receiver could enforce the disabled preference. A tile could also replay a relative toggle after its first mutation succeeded but later observation failed. Decision: keep inventory read-only, let existing activity/boot/always-on owners request restoration explicitly, and retain one interactive request per manager. Boot/shutdown receivers acquire `goAsync` before backend selection and finish the pending result on coroutine completion, including cancellation before execution. Running-name saving also awaits inventory before replacing persisted intent. Tile consent carries the original managed object and an absolute target through a local Binder and retained ViewModel; it is admitted only for the actual UP authorization failure.

Keeping the receiver's preference check beside forced initialization cannot stop the earlier activation. Repeating every failed relative toggle can invert an already-applied result. Neither alternative preserves caller policy. The chosen repair keeps existing application/lifecycle scopes, manager admission, platform Binder and ViewModel owners; it adds no startup framework, persistent request registry or scheduler. Asynchronous receiver work remains subject to Android's bounded broadcast lifetime; host completion controls do not prove the Android timeout or process-retention boundary. Missing/dead/process-restored tile continuations require a new user action. The source decision is implemented; focused host/fragment proof and publication belong to its PR, while native boot/Binder/lifecycle and release acceptance remain separate. [Backend contracts](backend-contracts.md#wireguard-configuration-and-tunnel-state) own detailed settlement and recovery limits.

### Preserve private ownership through client-key rotation — #143, 2026-10-17

**Problem/decision; source candidate:** replacing a public peer key before durably retaining its new private profile could strand the client. Extend the existing Fragment/ViewModel, pending-intent store, encrypted vault, provisioning client and script transaction owners. Encrypt a local proposal first; use explicit PREPARED/DISPATCHED/REJECTED public intent and proposed/settled private ownership. Verify exact preserved settings remotely, atomically settle the vault, then retire the exact public intent. Keep lock order store then vault; network work remains outside those locks.

**Alternatives/consequences:** remove-plus-add would change address/settings and create a wider failure window. Public status cannot prove PSK preservation; read-only exact verification is required after uncertainty, with no replay or key regeneration. Locally imported/exported copies remain separate and must be replaced explicitly. Prior strict v1 readers reject the whole vault while rotation metadata remains, including cleanup orphans; supported recovery must finish before downgrade. [The contract](backend-contracts.md#confirmed-client-key-rotation--143) owns admission, compatibility and crash boundaries. [Scoped local source/output checks](qa-test-plan.md#client-key-rotation-controls--143) pass; final integration/publication and installed/native/live acceptance remain separate. No new service, scheduler or mutation framework is added.

### Stage pinned native source for supported Go overlays — #215, 2026-10-17

**Problem:** the former Go 1.24.3 runtime/module pins are outside the selected supported release lines and retain advisory version matches. Go 1.26 rejects the existing overlay's module-cache targets. Updating the compiler alone therefore breaks the native build and host ownership controls.

**Decision/status:** the authorized #215 maintenance source selects Go 1.26.9, `x/crypto v0.58.0`, `x/net v0.61.0` and `x/sys v0.49.0`. The WireGuard pin and runtime patch remain unchanged. Extend the existing overlay generator: validate the original exact pin/reject original replacements, refresh a per-output copy of upstream source, then generate private module files with one relative local replacement. Apply the same exact-match overlays to that stage. Android Make and host tests pass the generated module file explicitly; production per-ABI stages and the host stage remain distinct. Go's standard package cache handles rebuilds without the old module-index override.

**Alternatives and consequences:** a compiler-only upgrade cannot keep module-cache overlays working. Vendoring would expand the maintained generated source/module tree beyond this adaptation. Selecting Go 1.26 preserves its macOS 12 minimum; Go 1.27 raises that minimum to macOS 13. The staged-source approach adds an owned disposable copy without changing tracked dependency source or shared cache bytes. A generated local replacement omits the original dependency h1 from embedded Go metadata, although the required version remains. Keep original `go.sum`, verified download identity and explicit source/cache comparisons as provenance. `go mod verify` passed in this run; ordinary product builds do not execute it on every invocation. Relative replacement metadata avoids embedding an absolute workstation path.

**Verification and limits:** [the dated maintenance record](reviews/2026-10-17-native-toolchain-maintenance.md) owns the native race/JNI, four-ABI, unchanged patch, incremental, notice and exact-artifact scanner evidence. Separate-package API24 x86_64 activation, authenticated loopback traffic, retained-session rebind and explicit DOWN pass there. The packaged stripped arm64 library has no scanner symbol inventory; its byte-matched unstripped counterpart provides bounded symbol evidence.
