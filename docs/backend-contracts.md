## WireGuard configuration and tunnel state

AmneziaWG is not accepted by the current parser/backends. The [2026-10-09 engine assessment](reviews/2026-10-09-amneziawg-engine-assessment.md) records the pinned official candidate, complete field/native/API 24/license matrix and proposed WG/AWG pre-initiation packet separation under [#76](https://github.com/novakin/wireguard-android/issues/76). Engine/field selection remains open; this assessment changes no accepted attributes, persistence, backend or packet behavior.

The existing [Config](../tunnel/src/main/java/com/wireguard/config/Config.java), Interface, Peer and endpoint/address types own parse/serialize behavior. Preserve repeated list fields, multi-peer profiles, IPv6 endpoint syntax and other supported WireGuard fields. Generated provisioning profiles must pass these same parsers/import paths.

| Section | Accepted attributes |
| --- | --- |
| Interface | `Address`, `DNS`, `ExcludedApplications`, `IncludedApplications`, `ListenPort`, `MTU`, `PrivateKey`. |
| Peer | `AllowedIPs`, `Endpoint`, `PersistentKeepalive`, `PresharedKey`, `PublicKey`. |

Private/public key requirements and value validation belong to those parsers. Peer Endpoint is optional; IPv6 endpoint literals use `[address]:port`. Unknown attributes, including wg-quick hooks and `SaveConfig`, are rejected. DNS serializes when servers or search domains exist, preserving domain-only and mixed IPv4/IPv6/search-domain profiles across save/export round trips. Existing ordering groups servers before search domains; repeated entries retain the parser's set semantics. Explicit prefixes must be 0–32 for IPv4 or 0–128 for IPv6; negative or oversized values throw ParseException, wrapped with the existing Interface Address/Peer AllowedIPs location by config parsing. Omitted prefixes remain host masks (32/128). #16 merged these repairs in PR #26; no file migration or automatic rewrite is performed.

Backend state uses `DOWN`, `UP` and `TOGGLE`. `TunnelManager` uses TOGGLE as an in-progress observable transition; it is not proof of an active VPN. Its coroutine mutex serializes mutations and state snapshots. Waiting admission remains cancellable; admitted operations finish backend/store/model reconciliation before propagating caller cancellation. Explicit DOWN queues behind earlier UP/TOGGLE, including requests not yet admitted. Deleted model references cannot reactivate a tunnel. Delete disconnects the observed backend before removing persistence/model ownership; failed deletion attempts restoration. Failed config saves retain the cached/persisted profile and attempt runtime restoration; recovery errors remain attached to the failure.

Initialization settles inventory waiters on failure/cancellation and retries failed loads. Inventory becomes available before automatic restoration; restoration children stay attached to their caller. Application backend initialization also settles cancellation instead of publishing fallback success. Backend notifications reconcile current observed state under the same manager lock; they preserve persisted restoration intent after spontaneous service loss. Explicit manager requests own changes to that intent. Detail config/statistics completions require the same binding and selected tunnel; destroyed views cancel their jobs. These scoped repairs merged in PR #25; complete kernel transition serialization merged in PR #27 under #15 as described below.

Backend switching drains prior transitions and disconnects tunnels under the manager admission lock before changing the preference. After that commit, queued mutations are rejected until restart; failed/cancelled restart restores the previous preference and releases the reservation. Shutdown failure can leave already-stopped tunnels down with their profiles intact, but restores usable controls. Preference rollback failure remains visible and keeps the reservation; it is not successful switching.

`GoBackend` manages Android VpnService and userspace/native activation; `WgQuickBackend` manages root/kernel commands. Preserve required permission/service setup and explicit ordering. A stale/destroyed service must not be reused; teardown cannot block the main thread waiting for long activation.

The native tunnel handle owns a standard Unix listener and accepted clients through `uapiserver.Server`. `Listen` preserves `/data/data/<application-id>/cache/wireguard/<interface>.sock`, creates new directories privately and applies socket mode 0600 before serving. It refuses an active socket, bounds the local probe to one second and replaces a stale socket only after connection refusal and confirmation that the path is a socket. Access denial, unexpected probe errors and non-socket paths are not treated as stale success. Teardown closes/unlinks the listener, waits for admission to stop, closes remaining clients and waits for their `IpcHandle` handlers before closing the device. Startup failures follow the same ordering. Closing a client unblocks an idle or partial request holding the pinned IPC lock; it does not roll back admitted settings. The Android owner replaces upstream queued acceptance, file duplication and deletion-watcher goroutines; unlinking the socket externally does not terminate the native device. Failed initial settings close the complete owned device. These source controls do not change Java service/config/port behavior or establish physical-device teardown proof; [#66](https://github.com/novakin/wireguard-android/issues/66) delivered the shared UAPI/build repair in PR #67. [#68](https://github.com/novakin/wireguard-android/issues/68) subsequently delivered the enclosing Java/native query-admission repair through merged PR #69 at `6bb17579`; native warm-up retains its bind/JNI owners.

Current userspace source passes `GoBackend`'s exact `VpnService` and originating activation thread to JNI. The Android-owned native bind opens a fresh `StdNetBind` generation, protects every available IPv4/IPv6 socket inside `Open` at creation/rebind, then publishes it for sends. The version/match-checked overlay guards unavailable-family descriptors with `-1, syscall.EINVAL`; at least one real descriptor must be protected. Protection failure closes the unpublished sockets and fails activation/rebind. Cookie/control sends share this readiness boundary. The native context attaches/detaches callback workers; startup callbacks also check the originating thread's interrupt flag. Expected liveness/interruption exceptions and unexpected Java throwables retain their identity when JNI rethrows them on startup, the next native query or shutdown.

Warm-up eligibility comes from explicit UAPI ListenPort intent: nonzero enables it; absent/zero disables it, including later automatic reopens. One one-byte zero datagram attempt precedes each outgoing type-1 initiation on the same captured generation and Endpoint. Responses, cookies, keepalives and data get no extra packet. Expected warm-up I/O failure still permits the ordinary initiation; cancellation, descriptor closure and unexpected errors propagate. Recheck service/generation after potentially blocking warm-up before sending the initiation. WireGuard owns retry/rekey timing; add no sleep, acknowledgment, retry worker, timer or wake lock. The narrow pinned-source build overlay preserves the requested port on failed bind setup and closes bind/route-listener ownership on mark failure; cached upstream source is not patched and persisted profiles are unchanged; a cold build may download the validated module.

Shutdown marks the bind terminal and closes sockets to release blocked sends, stops/drains UAPI clients, closes the device and only then releases JNI references. The handle table admits reads without waiting under its lock and removes a closing handle before cancellation. Teardown cancels bind/UAPI I/O before draining admitted queries, then closes the device and releases JNI references. IDs increase without reuse within the native process, so a delayed lookup cannot acquire a replacement context; exhausting nonnegative 32-bit IDs fails startup. Java snapshots the tunnel/handle under its state lock, queries outside that lock and discards a result after identity changes. Java clears owned tunnel state before native teardown and publishes DOWN/restores service acquisition in cleanup even if JNI rethrows a callback defect. Existing transition ownership, service identity, config serialization and kernel behavior remain intact. Native warm-up replaces the separate Java five-attempt/200 ms preflight loop and late ignored socket-protection calls. Retained baseline APK/source and historical lifecycle/TrafficStats evidence keep their original scope; [source evidence and remaining physical limits](reviews/2026-10-07-protocol-preflight-experiment.md) own verification. The maintainer authorized adoption through PR #63 on 2026-10-08 (Europe/Paris). PR #63 records exact-head review/checks and actual delivery state. #61 remains open for physical, unchanged-server and DPI acceptance.

The historical [#37 compatibility decision](reviews/2026-10-07-udp-compatibility-review.md) rejects recovery of the preserved mandatory/random-port variant: it would reject endpoint-free profiles, replace configured ListenPort and remove merged lifecycle guards. Its extra packets, sleeps and new error/locales are not accepted behavior. That decision does not prove warm-up benefit or native port/NAT handoff; a future policy change needs a concrete reviewed requirement and authorization.

The prior Java socket owner's TrafficStats tag isolation is historical behavior under [#55 regression evidence](reviews/2026-10-07-g4-settings-add-debug-review.md) and its [candidate-device observations](reviews/2026-10-07-g4-candidate-device-review.md). Its socket/tag tests are replaced here by native-owner controls; no native accounting or battery improvement is claimed. Settings still probes kernel support on IO in its existing lifecycle coroutine, with native preference changes and pending Connection visibility on Main.

In retained baseline logs, `UDP preflight sent` means the protected Java socket accepted a local send. It does not acknowledge delivery or DPI resistance. Native warm-up adds no per-packet success log or server acknowledgment and leaves the WireGuard protocol unchanged. Socket continuity and authenticated loopback traffic do not establish hardware deep suspend, broader unchanged kernel-server compatibility or DPI benefit. The maintainer's 2026-10-08 report of sleep/wake recovery without manual action is not new measured packet/timing proof; the earlier 195-second forced Doze trial retains its own scope in [the experiment record](reviews/2026-10-07-protocol-preflight-experiment.md#forced-deep-doze-recovery--2026-10-07). The [G4 investigation](reviews/2026-10-07-g4-preflight-investigation.md) retains its separate incident/port-change scope. No DPI, speed or battery gain is established.

`WgQuickBackend` serializes the entire transition on its existing instance: observed state, config snapshot, prior-tunnel shutdown, apply, rollback, map update and callback. Running-name reads and multiple-tunnel preference changes share that monitor. Application collects those mode changes on IO, so waiting behind a root transition leaves the main thread free. Disabled multiple mode admits one app-owned active tunnel; enabled mode retains supported simultaneous tunnels. Failed apply/shutdown attempts restoration where applicable; restoration failures attach to the primary exception and observed running names remain queryable. RootShell still serializes individual commands; the backend monitor additionally protects the whole transition. This does not coordinate another backend instance or external root tools, turn multi-command changes into kernel transactions, or guarantee observation after an unreachable shell. #15 has controlled command-level JVM proof; device/kernel traffic and partial native effects remain separate.

## Import, ordering and export

`TunnelComparator` retains natural numeric ordering and uses the original names to break equal normalized-token ties. Distinct names such as `wg1`/`wg01` and case variants remain distinct inventory entries; lookup must not depend on insertion direction. Names and persisted files are not rewritten.

`TunnelImporter.importTunnel(ContentResolver, Uri, callback)` owns its profile-creation children in a supervisor scope. Expected input/parsing failures and failed creations contribute to one final result after creations settle; an invalid or duplicate ZIP entry does not cancel valid siblings. Cancellation and unrelated Errors escape without an import-failure callback. Callback defects escape once; they are not converted into a second delivery. Import logs record failure class only, excluding config/parser payloads. A naming dialog still owns text/QR imports and retains the separate C8 naming gaps.

QR image retries reopen input for each sample scale and recycle allocated bitmaps in `finally`. Reader failures, invalid decoding and allocation pressure can retry; cancellation, I/O denial and unrelated Errors escape. Exhaustion preserves the first recoverable failure; allocation failure becomes IOException with its original OutOfMemoryError cause so existing import feedback can report it. Tests use synthetic bitmap/provider/reader faults rather than camera/device memory exhaustion.

`ZipExporterPreference` owns awaited config-loading children and restores its control in `finally`. `DownloadsFileSaver.save` owns acquisition, metadata lookup, the synchronous writer callback, stream closure and failure cleanup on IO; it returns a completed path or null for denied legacy storage permission, never a live output resource. A failed open/query/write/close or observed cancellation triggers cleanup of the owned incomplete output. MediaStore ownership starts at insertion; legacy ownership starts only after opening the file, so a failed open does not delete a pre-existing path. Cleanup is synchronous on IO even after cancellation and any failure is suppressed onto the primary Throwable before rethrowing. Provider deletion returning zero and filesystem deletion returning false are explicit cleanup failures, not proof of removal.

Cancellation checks surround the writer, but blocking ZIP writes are not interruptible. Cancellation during a write is handled after it returns and the stream closes. A completed file can remain if prompt cancellation discards the path at the final dispatcher return; no live-resource handoff exists and no success feedback is produced. The authorized same-name overwrite policy and ZIP entry/config serialization are unchanged; overwrite is not transactional recovery of an older export. Pending permission results remain tied to the current legacy request; a rejected launch clears its cached waiter before propagating the failure. [Downloads evidence](development.md#downloads-output-ownership--2026-10-07) separates synthetic API 28/29 proof from unperformed physical-provider checks in G4.

## Provisioning command surface

The [client](../ui/src/main/java/com/wireguard/android/provisioning/TunnlProvisioningClient.kt) uploads [packaged scripts](../ui/src/main/java/com/wireguard/android/provisioning/ProvisioningScriptBundle.kt) to a temporary remote directory, constructs quoted commands, parses JSON and attempts cleanup. Commands requiring root run directly for root or through non-interactive `sudo -n`. Concrete SSH execution is not implemented yet.

Current server assumptions: Ubuntu/Debian, default `wg0`, IPv4 `/24` allocation, IPv4 default routes and iptables NAT. Script environment overrides do not establish a validated live platform/interface matrix. Plan/install/peer value options reject missing values and config-injection tokens. C2–C3 mutations enforce ownership, native locks, private snapshots and checked postconditions; this is offline source/test proof, not a real VPS run. The [script guide](../third_party/wireguard-install/tunnl/README.md#ownership-locking-and-recovery) owns validation, lock order, stopped-interface semantics and recovery limits. Read-only/pre-transaction shell failures are not uniformly JSON-guarded.

| Command | Current inputs | Result fields used by Android | Known gap |
| --- | --- | --- | --- |
| `detect.sh` | No app arguments. | OS/version/support, package/firewall, installed/config state, interface/endpoint/port/CIDR/forwarding. | Endpoint comes from config metadata, not public-IP discovery; detection is not connectivity proof. |
| `plan.sh` | `--endpoint`, `--port`, `--cidr`, `--dns`, optional `--force`. | Support Boolean, endpoint/port/CIDR/DNS, overwrite flag and steps. | Force is accepted for the shared request; planning stays advisory and read-only. Ownership/root/runtime feasibility is checked by install. |
| `install.sh` | Same fields plus optional `--force`. | Interface/endpoint/port/CIDR and server public key. | Ownership and effective runtime are checked; package/global forwarding effects are not transactional. Live proof remains separate. |
| `sync-status.sh` | No app arguments. | Interface/running/config metadata and peer name/key/AllowedIPs/handshake/RX/TX. | Native interface observation is true/false/null. Missing or invalid runtime counters are null; neither interface presence nor a timestamp proves connectivity. |
| `add-peer.sh` | App sends required `--name` and `--allowed-ips`, plus optional `--dns`. | Name/address/public key and full generated client config. | Serialized disk/apply/recovery checks exist; stopped interfaces receive disk-only changes. The profile contains a private key. |
| `remove-peer.sh` | `--name`. | Name, `removed:true`, `revoked:false`. | Effective running-peer removal and recovery are checked; stopped-interface changes remain disk-only. |
| `revoke-peer.sh` | `--name`. | Name, `removed:true`, `revoked:true` and archive path. | A unique secret-bearing archive follows checked removal. |

| `uninstall.sh` | Required `--confirm`, optional `--purge-packages`. | Uninstalled/backup/packagesPurged. | Ownership, service/config absence and requested package absence checked. Partial package effects may prevent restoration. |

Do not use invented success fixtures to hide producer/consumer drift. Add fixtures from actual script responses and explicit assertions for intentional compatibility changes. Preserve unrelated server state and global forwarding; validate ownership and inputs before privileged writes.

Plan runs without root. `willOverwriteConfig` observes a visible regular file; restricted path access can hide an existing config. It is not overwrite approval or an exact install feasibility result. The force flag only changes install's replacement permission after ownership checks.

## Result, error and cancellation meaning

`ProvisioningCommandOutput` carries exit code/stdout/stderr. A zero exit passes `requireSuccess`; nonzero throws a category/exit-code exception while retaining the internal output for the responsible caller. Internal output may contain secrets and is not a diagnostic string.

`RootShell.run()` preserves returned stdout, marker framing and exit status without logging commands or stream payloads. Root startup diagnostics also omit raw UID/error output. Provisioning command failures log only their exit code/category. `ProvisioningJson` guards the full response, including nested arrays and peer rows; shape/parser failures carry no output or parser cause. Cleanup warnings omit exception payloads and preserve the completed result. [C1 evidence](development.md#c1-secret-safe-logging--2026-10-06) retains its historical scope; [C4 evidence](development.md#c4-provisioning-contracts-and-observed-health--2026-10-06) covers strict schemas and remote errors. C9 now applies payload-free failures to the disposable harness; future transport diagnostics still need handling at their owner.

JSON requires an actual `ok` Boolean. Consumed success strings, Booleans, arrays and nested objects are required and strictly typed, except optional `cleanupPath` and remove-only `archive` strings. Revoked success requires a nonblank archive string. Plan requires `supported:true`; peer mutation requires `removed:true`; uninstall requires `uninstalled:true`. Unknown extra fields are ignored. Numeric counters are decimal strings bounded by signed Long; `revokedCount` is bounded by signed Int. Running and peer handshake/RX/TX fields require Boolean/decimal-string or explicit null as appropriate. Null means unavailable observation, zero means an observed zero; missing fields and invalid/negative/overflow values are invalid responses.

Legacy string-only mutation results are intentionally rejected. The app uploads its packaged bundle per operation; pair the parser and scripts from the same reviewed revision.

Structured failures require string `error` and `message` fields, but remote text never becomes diagnostics. `ProvisioningFailureCategory` supplies fixed messages; the allowlist in `ProvisioningJson.remoteFailure` supplies a safe `remoteCode` only for supported codes. Unknown codes map to REMOTE_FAILURE without retaining the code. Missing/malformed fields map to INVALID_RESPONSE. Script execution consumes `ok:false` even on a nonzero exit, preserving the safe category/recovery; nonzero `ok:true` is still command failure. Generic command failures retain internal output under the contract above.

C2–C3 mutation failures additionally expose `recovery`, `recoveryPath` and `artifact`. Android keeps only the recovery enum: UNCHANGED, RESTORED, INCOMPLETE or UNKNOWN for an unrecognized/malformed present value; absent recovery stays null. INCOMPLETE/UNKNOWN adds a fixed inspection warning. Untrusted recovery paths/artifact text are not retained in exceptions. Successful install/add/remove/revoke/uninstall models expose optional `cleanupPath` (empty when absent or clean). Live UI presentation of recovery/cleanup remains C12; operator handling follows [operations](operations.md#provisioning-mutation-recovery).

The existing guarded shell boundary has a 30-second default execute/upload coroutine timeout, preserves cancellation and maps expected IO failures. Factory checks require a fingerprint when trust is disabled and at least one auth attempt. These are wrapper checks, not proof of host-key verification or real channel/session closure. C11 must implement and test those behaviors against the chosen SSH library.

Command success is limited to the requested operation's effective postconditions. Interrupted or timed-out remote operations have uncertain outcomes until reconciled. Revocation must remove live access; installation results must match runtime config; uninstall/purge results must reflect observed removal. Rollback/recovery failures must remain visible.

The [disposable harness](qa-test-plan.md#disposable-vps-integration-use-case) requires `running:true` for `wg0`, exact saved name/key membership and the same complete native `wg show wg0 peers` key set after each install/add/revoke/remove. Uninstall checks `uninstalled:true`, the exact requested `packagesPurged` Boolean, detect's config/tools state, actual config/symlink absence and native interface absence under available `/sys/class/net`. Purge additionally checks `wireguard`, `wireguard-tools` and `qrencode` as absent/not-installed through `dpkg-query`; residual `config-files` status or query failure fails. Keep-packages requires retained `wg` availability. Only fixed local stage/category/exit diagnostics are emitted, including malformed/nested JSON and cleanup failures. Offline injected controls establish these decisions; they establish no SSH, systemd, package or packet behavior. [Cleanup ownership and uncertain outcomes](operations.md#disposable-validation-and-recovery) remain explicit.

## Persistence and presentation

Quick Settings membership is a nullable confirmation in the existing settings DataStore, independent of `TileService` creation, destruction and listening. `QuickTileService.onTileAdded` and native request results `TILE_ADDED`/`TILE_ALREADY_ADDED` persist true; `onTileRemoved` persists false. Missing pre-repair confirmation remains unknown, not proven absence. Writes use the application scope and existing serialized DataStore transactions, so normal activity/service teardown does not cancel them; app-process reconstruction retains committed values. Abrupt process termination before a write commits, persistence failure and notifications Android has not delivered remain outside that guarantee. Expected persistence failures retain prior data and log a fixed category without inventing an absent confirmation.

`UserKnobs` owns a process-local removal revision. Each native Add request and add notification captures that revision before asynchronous confirmation work; actual removal advances it synchronously before its false write is launched. A true confirmation checks the captured revision inside the DataStore transaction and skips its write after any later removal. Native request results and service notifications use independent callback channels, so a late successful/already-added result must not reassert membership after a genuine removal, including after Settings destruction. A new add notification/request captures the current revision and remains eligible. Process termination discards old callbacks; the revision needs no persistence or settings-format migration, while committed membership remains durable.

Android 13+ Settings keeps its Add tile row hidden until membership loads, then hides confirmed membership and offers the native idempotent fallback for false or a loaded value without recorded confirmation. A view-lifecycle observer applies later confirmations and removals while Settings stays open; stopping/recreating its view releases and reloads observation. An unavailable read keeps setup hidden until a later lifecycle observation loads confirmation; it never writes absence. Request cancellation and reported native errors do not record membership; existing visible Snackbar/background Toast feedback remains. Android versions below 13 still omit the setup action. No platform inventory query, new service or tunnel/backend behavior is added. [#85](https://github.com/novakin/wireguard-android/issues/85) owns independent native inventory/reopening acceptance.

`ObservableTunnel.statistics` is a cache-only bindable getter; it starts no backend work. Existing Home, Detail and TV pollers use nullable `getStatisticsAsync`, routed through `TunnelManager.getTunnelStatistics`. A fresh snapshot from the current backend/session is reused without copying or retimestamping; `Statistics.isStale` remains true only after more than 900ms. Equivalent stale/missing readers share one manager-owned in-flight request for the same managed tunnel identity, generation, backend instance and name. Admission uses the existing mutation lock briefly; backend IO and reader waits run outside it.

Before publishing on Main, the manager checks caller/application liveness, request identity, managed membership, UP state, generation, name and backend identity. DOWN/TOGGLE, reconnect, admitted config/rename/delete work and backend switching invalidate affected sessions. Backend `onStateChange` advances an `AtomicLong` generation immediately on its callback thread, before queued Main reconciliation; even a rapid DOWN/UP pair cannot preserve the old cache. Cache reads reject a snapshot tagged with an earlier generation. TV clears and hides its transfer row when the result is unavailable.

Each reader owns its wait, not the shared request. Cancelling one reader preserves work needed by others; the last reader removes its request and cancels its shared read. Ordinary unavailable/obsolete sessions return null so still-active pollers can continue. A new request through an unmanaged tunnel retains `NotManagedException` rejection; an already-admitted read invalidated by deletion returns null. Owner invalidation is identified by its exact cancellation cause; genuine caller, application or backend cancellation propagates, as do backend failures and `Error`. Completed failures are not converted into obsolete success. Failed/cancelled requests can be retried. `runInterruptible` supports interruption of cooperative blocking Java work, not a guarantee that blocking JNI returns; native owners retain teardown responsibility.

These are the separately authorized [#48](https://github.com/novakin/wireguard-android/issues/48) source contracts. Its PR owns executed checks, review and delivery state. The [G2 investigation](reviews/2026-10-07-performance-source-investigation.md) preserves the original defect evidence. This source change establishes no physical VPN behavior or speed/battery gain.

Home selection stores managed tunnel identities, not numeric row positions. Saved names are recreation inputs only; restored views require a new destructive confirmation. Rename preserves inventory membership during store I/O and synchronously reindexes the same instance on Main under the manager's mutation lock. A confirmation captures current instances, updates observed warnings and is dismissed when a snapshot member leaves inventory or its owning view is destroyed. Only the current, showing dialog can admit its captured snapshot; a dismissed callback cannot consume a later confirmation's intent. A same-name replacement is never admitted through the stale instance. The manager identifies stale ownership with internal NotManagedException, preserving the prior IllegalStateException superclass/message; other unexpected runtime defects propagate through bulk deletion. Confirmed bulk deletion reuses the manager's serialized delete/rollback contract sequentially; cancellation stops remaining work after admitted settlement. Partial feedback reports observed removed/remaining snapshot members, and survivors remain selected. No persistence format, multi-peer/config parsing or backend transition policy changes. See [Home source proof and physical limits](development.md#home-selection-and-safe-delete-recovery--2026-10-07).

`FileConfigStore` preserves `.conf` names and wg-quick serialization. Its single app-owned instance serializes create/save/load/enumerate/rename/delete. Create/save write a unique private `.tmp` in the same directory, sync and close it, then atomically rename it to the target. Failed write/sync/rename reports IO failure and retains the prior profile; failed create publishes no profile. Rename rejects an existing destination without creating a marker. Temporary cleanup is attempted and failures log no profile payload. Process death can leave a private ignored `.tmp`; no automatic deletion of existing files or migration is performed. This does not establish directory durability under power loss or coordination with external writers/other store instances. See [architecture decision](architecture.md#local-profiles-commit-through-native-atomic-rename) and [focused evidence](development.md#atomic-local-profile-replacement--2026-10-06).

`VpsServerStore` keeps non-secret fleet metadata and nullable running observations through existing DataStore transactions. Legacy records without `running`, and malformed running types, remain usable with unknown health. Status updates persist true/false/null without retaining an earlier observation. Corrupt-store warnings exclude payloads/parser causes. Protected SSH credential persistence remains separate.

`VpsDeployMapper` maps incomplete endpoint/CIDR to PROVISIONING. Complete records need a positive, nonfuture sync timestamp at most 600 seconds old: running true maps ONLINE, false OFFLINE and null ATTENTION. Missing, future or older timestamps map ATTENTION regardless of old running evidence. Recent-sync and running health checks express separate facts; stale running health is unknown. ONLINE means recently observed interface presence, not a successful handshake, route, NAT, DNS or packet test. Peer ACTIVE requires running true and a nonfuture positive handshake at most 180 seconds old; unavailable counters render as an em dash.

UI presentation must use actual selected/view-owned data. Abbreviated keys remain display-only; copy/export/QR need the complete authorized payload. The manager publishes the resolved transition target before entering `TOGGLE`. A pending disconnect renders DOWN with its switch off and disabled; a pending connect renders CONNECTING with its switch on and disabled. Settlement clears the target, including failed-disconnect restoration to observed UP. State is updated before statistics-clear notifications so bindings cannot briefly classify a disconnect as connecting.

RX/TX bindings share one cached result for each `Statistics` snapshot. A fresh snapshot with unchanged counters publishes zero after the minimum sample interval; repeated reads of that same snapshot retain its result. Rapid snapshots accumulate traffic until that interval, counter rollback restarts the baseline, and absent statistics clears the baseline for reconnect. These are display calculations, not packet-health proof. See [regression and device evidence](development.md#phone-ui-and-throughput-follow-up--2026-10-06).
